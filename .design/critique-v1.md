## 🟡 Важные проблемы (Should Fix)

### 1. Коллизия с существующим полем `Transaction.category` (String)

**Где:**
- `app/models/database.py`, строка 109
- Solution: добавление `category_id` FK

**Проблема:**
В текущей модели уже существует поле `category = Column(String(100))` (строковое). Решение предлагает добавить `category_id = Column(Integer, ForeignKey(...))`. Это создает два поля с похожими именами и разной семантикой:
- `category` (String) — старое поле "на будущее"
- `category_id` (FK) — новое поле для связи с Category

**Почему важно:**
- TransactionService уже использует `category` (строка) в create/update методах
- Dashboard показывает `tx["category"]` в UI
- Может возникнуть путаница между полями
- Необходима миграция данных (хотя все `category` сейчас NULL или пустые)

**Рекомендация:**
Решение должно явно описать судьбу старого поля `category`:
1. **Вариант A**: Удалить `category` (String), заменить на `category_id` (FK) — breaking change
2. **Вариант B**: Переименовать `category` в `category_legacy` или `category_note` для обратной совместимости
3. **Вариант C**: Оставить оба (category для заметок, category_id для структурированной категории)

**Рекомендуемый подход**: Вариант A (удаление) — поле не используется реально, данных нет, проще сделать clean break.

### 2. Неопределенность ADJUSTMENT в статистике (Dashboard, Year Summary)

**Где:**
- `app/services/dashboard_service.py`
- `app/services/calendar_service.py` — `get_month_summary()`, `get_year_summary()`

**Проблема:**
Решение описывает, как ADJUSTMENT влияет на баланс (`_calculate_balance_before_date`), но не уточняет:
- Включается ли ADJUSTMENT в `total_income` или `total_expense` в сводках?
- Как отображается в cashflow графике?
- Должен ли быть отдельный тип "Корректировки" в метриках?

**Пример проблемного сценария:**
1. Пользователь имеет total_income = 100,000, total_expense = 80,000
2. Создает ADJUSTMENT +5,000 (обнаружил неучтенный доход)
3. Ожидание: total_income = 105,000
4. Реальность с текущим решением: непонятно, куда попадет ADJUSTMENT

**Рекомендация:**
Явно определить поведение ADJUSTMENT в статистике:
```python
# Вариант A: ADJUSTMENT не входит в income/expense (только баланс)
# Это логичнее — корректировка не является реальным доходом/расходом

# Вариант B: ADJUSTMENT с положительным amount -> income, отрицательный -> expense
# Это запутывает пользователя

# Рекомендуется Вариант A + отдельная метрика "Всего корректировок" в UI
```

### 4. Формула ADJUSTMENT может быть неочевидна для пользователя

**Где:**
- `ReconciliationService.create_adjustment()`
- Формула: `adjustment_amount = actual_balance - expected_balance`

**Проблема:**
Если expected = 10,000 и actual = 8,000, создается ADJUSTMENT = -2,000. Пользователь может не понять, почему "добавляется" отрицательная операция. UI должен явно объяснять.

**Рекомендация:**
В модале сверки показывать:
```
Расчетный баланс: 10 000 ₽
Фактический баланс: 8 000 ₽
Разница: -2 000 ₽

[!] Будет создана корректировка на -2 000 ₽
    Это означает: в учете было "лишних" 2 000 ₽, которых нет в реальности
```

## 🔄 Альтернативные подходы

### Подход A: Tag-based категоризация

**Идея:**
Вместо одной категории на транзакцию — множество тегов (many-to-many).

**Плюсы:**
- Гибче: транзакция может быть "Еда" + "Ресторан"
- Лучше для аналитики

**Минусы:**
- Сложнее UI (multi-select vs dropdown)
- Сложнее фильтрация
- Overengineering для MVP

**Рекомендация:** Не стоит для Батча 3.1. Можно рассмотреть в будущем.
