## 🔴 Критичные проблемы (Blockers)

### 1. Отсутствие детализации Edit Goal callback с Pattern-Matching

**Где:**
- Секция "Ключевые интерфейсы" и план реализации Фаза 3
- В списке callbacks упомянут `open_edit_modal()`, но не показан его код

**Проблема:**
FR-05 (Редактирование параметров цели) требует Pattern-Matching callback, аналогичный `open_edit_modal` в transactions.py. Однако в solution показаны только простые toggle callbacks. Учитывая историю проекта с ADR-003 и проблемами Pattern-Matching, это критический пробел.

В отличие от transactions.py, где есть кнопки Edit/Delete для каждой строки таблицы, в goals.py планируется **одна** активная цель с кнопками действий. Это меняет архитектуру:
- Нужен ли Pattern-Matching вообще? (одна цель = одна кнопка)
- Если нет Pattern-Matching, то guard clauses из ADR-003 не нужны для Edit/Delete

**Почему критично:**
- Неясно какой паттерн использовать (Pattern-Matching vs simple callback)
- Риск повторения регрессий из Батча 2-4 (feature_progress.md)
- Блокирует начало кодирования без уточнения

**Рекомендация:**
Явно указать что для **одной активной цели** не нужен Pattern-Matching:
```python
# Простой callback без Pattern-Matching (одна цель = один ID в dcc.Store)
@callback(
    Output("edit-goal-modal", "is_open"),
    [
        Input("edit-goal-btn", "n_clicks"),  # Обычный ID, не dict
        Input("edit-goal-cancel-btn", "n_clicks"),
    ],
    State("current-goal-id", "data"),  # ID цели из Store
    prevent_initial_call=True,
)
def toggle_edit_goal_modal(edit_clicks, cancel_clicks, goal_id):
    ...
```

Либо явно обосновать почему Pattern-Matching нужен (например, для будущего множественных целей в Batch 2).

# 2. confirm-delete-goal.submit -> вызвать GoalService.delete_goal()

## 🟡 Важные проблемы (Should Fix)

### 3. Несоответствие UI State архитектуры между dcc.Store и reload pattern

**Где:**
- Секция "Модель данных (dcc.Store)"
- Callbacks: `load_goal_data()`, `add_contribution()`

**Проблема:**
Solution показывает два конфликтующих подхода:
1. `dcc.Store` с `goal_id` для передачи между callbacks
2. `load_goal_data()` который загружает цель из БД по `url.pathname`

При создании/добавлении взноса:
- `add_contribution` обновляет `goal-card-container` и `contributions-table-container`
- Но `current-goal-id` в Store может устареть если пользователь удалил цель или статус изменился

**Пример сценария:**
```
User добавляет взнос -> цель достигает 100% -> статус меняется на COMPLETED
-> goal_id в Store все еще указывает на эту цель
-> Кнопка "Добавить взнос" все еще активна (хотя не должна быть)
```

**Рекомендация:**
1. При каждом CRUD всегда обновлять `current-goal-id` Store
2. Добавить проверку статуса цели перед показом кнопки "Добавить взнос"
3. Или: убрать Store и всегда загружать активную цель из БД (simpler but more DB calls)

### 4. Отсутствие toggle_goal_status callback детализации (FR-08)

**Где:**
- FR-08: "Смена статуса цели (ACTIVE/PAUSED/COMPLETED)"
- В диаграмме есть `toggle_goal_status()`, но нет кода/описания

**Проблема:**
Смена статуса имеет бизнес-правила:
- ACTIVE -> PAUSED: всегда разрешено
- PAUSED -> ACTIVE: проверить нет ли уже активной цели (MVP ограничение)
- COMPLETED -> ACTIVE: технически возможно, но нужно ли?
- Любой -> COMPLETED: только автоматически при достижении цели

**Почему важно:**
- ValidationError в GoalService для "только одна активная цель" может сработать при попытке PAUSED -> ACTIVE если есть другая активная
- Нужно решить: разрешать ли manual COMPLETED или только автоматически

**Рекомендация:**
Добавить бизнес-правила для toggle_status:
```python
# Разрешенные переходы:
# ACTIVE -> PAUSED (всегда)
# PAUSED -> ACTIVE (если нет других активных - проверка в callback)
# ACTIVE/PAUSED -> COMPLETED (запретить вручную, только автоматически)

def toggle_goal_status(n_clicks, goal_id, current_status):
    if current_status == "PAUSED":
        # Проверить нет ли активной цели перед сменой на ACTIVE
        ...
```

## 🔄 Альтернативные подходы

### Подход A: Единый GoalCard компонент вместо отдельных callbacks

**Идея:**
Вместо множества callbacks для каждого действия, создать "умный" GoalCard компонент который управляет своим состоянием через один callback с "action" параметром.

**Плюсы:**
- Меньше callbacks (1 вместо 5-7)
- Проще тестировать
- Лучше инкапсуляция

**Минусы:**
- Отклоняется от паттерна transactions.py
- Сложнее для новых разработчиков

**Рекомендация:** Не использовать - лучше сохранить консистентность с transactions.py.

### Подход B: Real-time обновление через dcc.Interval

**Идея:**
Добавить periodic refresh для показа актуального статуса цели (если другой пользователь внес взнос).

**Плюсы:**
- Актуальные данные
- Подготовка к multi-user

**Минусы:**
- Усложнение для MVP
- Дополнительная нагрузка на БД

**Рекомендация:** Отложить до Batch 2+ когда появится multi-user.
