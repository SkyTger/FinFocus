## 🔴 Критичные проблемы (Blockers)

### 1. Отсутствует пересчет exception при изменении суммы существующего взноса

**Где:**
- Секция решения: "План реализации"
- Отсутствует интеграция с `update_contribution_transaction()` в BudgetReservationService

**Проблема:**
В brief.md явно указано: "При изменении суммы взноса exception должен пересчитываться". Однако в solution-v1.md нет упоминания об интеграции с методом `update_contribution_transaction()` (строки 434-494 в budget_reservation_service.py).

Текущий `update_contribution_transaction()` обновляет сумму транзакции и GoalContribution, но НЕ вызывает пересчет exception.

**Почему критично:**
```
Сценарий:
1. User создает взнос 5000₽ до даты резерва
2. Exception создается: резерв = бюджет - 5000
3. User редактирует взнос на 3000₽
4. Ожидание: резерв = бюджет - 3000
5. Реальность: резерв остается = бюджет - 5000 (exception не пересчитан)
```

**Рекомендация:**
Добавить вызов `recalculate_current_month_exception()` в `update_contribution_transaction()`:

```python
def update_contribution_transaction(self, transaction_id: int, new_amount: Decimal) -> bool:
    # ... существующий код ...

    # После обновления contribution, пересчитать exception
    if contribution and contribution.goal:
        user_id = contribution.goal.user_id
        self.recalculate_current_month_exception(user_id)

    return True
```

**Альтернативный подход:**
Модифицировать GoalService, чтобы он вызывал пересчет при любом изменении взноса через отдельный метод `update_contribution()`.

### 2. Граничное условие `reserve_date <= date.today()` некорректно

**Где:**
- Секция "Обработка ошибок", строки 246-247
- `recalculate_current_month_exception()`

**Проблема:**
Guard clause `if reserve_date <= date.today()` пропускает пересчет если дата резерва СЕГОДНЯ. Однако если пользователь делает взнос в день резерва (до момента генерации recurring экземпляра), exception должен быть создан.

**Почему критично:**
```
Сценарий (today = 15.02.2026, reserve_day = 15):
1. reserve_date = 15.02.2026
2. reserve_date <= today → True
3. Skip recalculation
4. Но recurring экземпляр еще не "материализован" в CalendarService
5. Взнос не уменьшит резерв в текущий день
```

**Рекомендация:**
Изменить условие на `reserve_date < date.today()`:

```python
# Guard: не пересчитываем только ПРОШЕДШИЕ даты
if reserve_date < date.today():
    logger.debug(f"Reserve date {reserve_date} already passed, skipping recalc")
    return False
```

## 🟡 Важные проблемы (Should Fix)

### 3. Неполная очистка orphan exceptions при изменении дня месяца

**Где:**
- Метод `_cleanup_orphan_exceptions()`
- Секция "Риски и mitigation"

**Проблема:**
Согласно solution: "Orphan exceptions не удаляются для старых шаблонов". Метод `_cleanup_orphan_exceptions()` вызывается только при смене дня, но существующие orphan exceptions от предыдущих багов останутся в БД.

Это может привести к:
- Некорректным суммам в _get_reserve_sum_for_month() если orphan exception попадает в range
- Confusion при debug если разработчик видит "призрачные" exceptions

**Рекомендация:**
1. Добавить в `_cleanup_orphan_exceptions()` логику удаления exceptions для остановленных шаблонов (с recurring_end_date в прошлом)
2. Или добавить migration script в план реализации для очистки существующих orphan exceptions

### 4. Отсутствует валидация что взнос связан с режимом fixed_date

**Где:**
- Метод `recalculate_current_month_exception()` в решении
- Связь с `adjust_reserve_for_contribution()`

**Проблема:**
В текущем `adjust_reserve_for_contribution()` (строки 576-661) корректировка вызывается для взносов ДО даты резерва. Но `recalculate_current_month_exception()` не проверяет есть ли взносы после даты резерва в текущем месяце.

**Сценарий:**
```
1. reserve_day = 15
2. User делает взнос 1000₽ 10-го числа → exception создается (резерв -= 1000)
3. User делает взнос 2000₽ 20-го числа (после резерва)
4. User удаляет взнос 10-го числа
5. recalculate() вызывается, но contributions_sum считает ТОЛЬКО взносы до reserve_date
6. Результат корректен, но неочевиден из кода
```

**Рекомендация:**
Добавить комментарий в код, объясняющий что contributions_sum фильтруется по `< reserve_date`, и это корректное поведение.

### 5. В плане реализации отсутствует порядок вызовов update_savings_budget → set_mode

**Где:**
- План реализации, пункт 6
- Callback `save_budget()` в goals.py (строки 2896-2906)

**Проблема:**
В текущем коде `save_budget()` сначала вызывает `goal_service.update_savings_budget()`, затем `reservation_service.set_mode()`. Однако `set_mode()` при создании нового шаблона берет бюджет из `user.monthly_savings_budget`.

Если порядок вызовов изменится или добавится параллелизм — возможен race condition.

**Рекомендация:**
Явно задокументировать порядок вызовов в решении:
```
1. update_savings_budget() — обновить User.monthly_savings_budget
2. set_mode() — использует НОВОЕ значение бюджета для шаблона
3. recalculate_current_month_exception() — использует НОВОЕ значение бюджета
```

## 🟢 Незначительные замечания (Optional)

### 6. EOM anchor логика может быть упрощена

**Где:** Метод `_get_template_day()`

Решение указывает: "Для EOM anchor (recurring_anchor_eom=True) возвращает 31". Однако реальный последний день месяца может быть 28, 29, 30 или 31. Возврат фиксированного 31 может путать при сравнении.

**Рекомендация:**
Добавить комментарий что 31 — это "anchor day", а не реальный день месяца. Либо возвращать `None` для EOM и обрабатывать отдельно.

### 7. Именование метода `_delete_exception_for_date` vs `_remove_exception_for_date`

**Где:** Интерфейсы, строка 113

Проект использует `delete` для удаления сущностей (`delete_goal`, `delete_contribution_transaction`). Но `remove` может быть более семантически корректен для exception который "снимает" переопределение. Несущественно, оставляю на усмотрение.

## 🔄 Альтернативные подходы

### Подход A: Event-driven пересчет через signals

**Идея:**
Вместо явных вызовов `recalculate_current_month_exception()` в каждом месте — использовать SQLAlchemy event listeners на изменение GoalContribution.

**Плюсы:**
- Централизованная логика пересчета
- Невозможно забыть вызвать пересчет

**Минусы:**
- Увеличивает coupling между моделями и сервисами
- Сложнее debug (неявные вызовы)
- Overhead для операций где пересчет не нужен

**Рекомендация:**
НЕ рекомендуется для MVP. Текущий явный подход предпочтительнее.
