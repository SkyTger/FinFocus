## 2026-08-28 (развилки цикла проектирования куска 3)

- **for: design-loop.** План Б для разворота полоски (FR-2/AC-5), решение
  владельца: **чинить, при неудаче — отложить**. Порядок: (1) дешёвая
  проверка гипотезы о переиспользовании узла на ЖИВОМ сайдбаре до любых
  удалений; (2) не сработало штатными средствами (стабильный `id` на
  кожухе) — разворот выносится в Epic-10, где уже лежит родственная
  анимация перехода дашборд↔раздел, а кусок 3 закрывается по остальным
  десяти критериям приёмки. Вариант с обработчиком в браузере,
  ослабляющий инвариант «у навигации ноль обработчиков», ОТВЕРГНУТ —
  проект чинил этот класс регрессий дважды (протоколы 0026, 0028).
  Прецедент частичного закрытия в эпике есть: кусок 2 закрылся с
  зафиксированным отступлением от FR-1.a.

- **for: design-loop.** Судьба `app/components/sidebar.py`, решение
  владельца: **оставить файл-надгробие**. Файл усыхает до
  `ADDITIONAL_NAV_ITEMS` + докстринг «остаток удалённого сайдбара;
  константа сохранена решением владельца 2026-08-27, вернуть иконку при
  появлении /settings или /help». Удаление файла целиком отвергнуто:
  трактовка «не трогать = удалить вместе с файлом» натянута, а прецедент
  «решение владельца можно обойти удачной трактовкой» дороже одного
  почти пустого файла. Следствия: чек-лист приёмки формулируется как
  «нет ни одного ИСПОЛНЯЕМОГО упоминания старого сайдбара (импорт, id,
  CSS-класс)», а не «ни одного вхождения строки sidebar».

- **for: design-loop.** Две развилки решены оркестратором по дефолту
  (легко переиграть, владельцу не выносились): (1) тест-сверка версии с
  git-тегом — ДОБАВЛЯЕТСЯ (скипается там, где git недоступен; ловит
  рассинхрон в момент постановки тега — то есть ровно дефект P3, который
  кусок и закрывает); (2) язычок-подсказка «Профиль» при наведении на
  аватар — ПРИНИМАЕТСЯ в кусок (тот же механизм, что у разделов, нулевая
  цена; без него аватар теряет подсказку, которая была в сайдбаре).
  Обе попадают в RTM и чек-лист приёмки.

- **for: design-loop.** Расхождение с раскадровкой эскиза, решение
  владельца 2026-08-28: **подписи важнее буквального роста плашки**.
  Установленный факт: в эскизе `.visual/finfocus-panel-rail/v4.html`
  класс раскадровки (`.frame-rail.cut`) висит на `.rail` — узле с
  фоном, границей, тенью и `overflow: hidden`, то есть схлопывается
  сама стеклянная плашка. Воспроизвести это буквально нельзя, не
  срезав всплывающие подписи разделов: они выходят за правую границу
  плашки, а обрезка идёт по её краю. Принято: плашка стоит сразу
  целиком, содержимое внутри проявляется сверху вниз. Отступление от
  раскадровки фиксируется письменно в RTM (тип Δ) — прецедент куска 2
  (окошко «вчера») действует. Путь с выносом подписей из-под обрезки
  отвергнут: все известные его варианты тянут обработчик в браузере,
  то есть тот самый вариант C, отвергнутый в Р1.
