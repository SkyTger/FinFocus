# Шаг 1: Маркировка и рендер служебных операций

## Briefing

- **Цель:** Список операций различает все шесть типов транзакций;
  служебные строки визуально помечены и лишены органов управления.
- **Ключевые файлы:**
  - `app/components/transactions.py` — `_build_transactions_table`
    (бейджи ~467-475, чекбокс ~510, кнопки ~509-530), `_build_chips_cell`
    (guard ~289-290)
  - `app/components/calendar.py:437-500` — ОБРАЗЕЦ (не править):
    readonly-строки, «(авто)», классы сумм
  - `app/services/transaction_service.py:410` — существующая подпись
    «Корректировка» (переиспользовать источник, не дублировать строку)
  - `tests/` — новый файл `tests/test_transactions_system_ops.py`
- **Доп. информация:** Служебные типы в этом протоколе:
  `SAVINGS_RESERVE`, `SAVINGS_CONTRIBUTION` (строго readonly).
  `ADJUSTMENT` и `TRANSFER` — пользовательские, но с честными бейджами.

## Sub-tasks

1. **Словарь отображения типов** (модульная константа в transactions.py):
   INCOME → «Доход» (success, «+»), EXPENSE → «Расход» (danger, «−»),
   TRANSFER → «Перевод» (нейтральный, без знака),
   ADJUSTMENT → «Корректировка» (нейтральный, знак по значению суммы —
   сверка календаря показывает adjustment со знаком, см. образец),
   SAVINGS_RESERVE / SAVINGS_CONTRIBUTION → «Накопления» (info/secondary,
   «−» — уменьшают баланс как расход, см. образец в календаре).
   Ввести хелпер-предикат `_is_system_transaction(tx)` — единственный
   источник правды «служебности» для шагов 1 и 2.
2. **Строки служебных операций** (savings-типы):
   - НЕ рендерить чекбокс bulk-выделения (пустая ячейка);
   - НЕ рендерить кнопки edit/delete — вместо них замок/текст «авто»
     с `title=`, поясняющим: «Системная операция — управляется через
     Цели» (SAVINGS_CONTRIBUTION) / «…через настройку резервирования»
     (SAVINGS_RESERVE);
   - к описанию дописывать «(авто)» — как в календаре;
   - CSS-класс приглушения строки (в `transactions.css`, по образцу
     `.readonly` календаря; новых глобальных токенов не вводить).
3. **Chips категоризации**: расширить guard в `_build_chips_cell` —
   к TRANSFER/ADJUSTMENT добавить оба savings-типа (показывать «—»).
4. **Решение Р1 (принять по факту осмотра, записать в log.md)**:
   осмотреть модал редактирования (`transaction_modals.py`) — умеет ли
   он тип ADJUSTMENT (есть ли в dropdown типов). НЕ умеет (ожидаемо) →
   у ADJUSTMENT скрыть кнопку редактирования, кнопку удаления оставить
   (корректировку сверки пользователь вправе откатить). TRANSFER не
   трогать — полноценная пользовательская операция.
5. **Тесты** (`tests/test_transactions_system_ops.py`, без БД — на
   объектах Transaction в памяти, по образцу test_dashboard_panel_ui.py):
   - параметризованный тест бейджа для всех 6 типов;
   - у savings-строки нет edit-btn / delete-btn / tx-checkbox в дереве;
   - у savings-строки без категории нет chips (есть «—»);
   - описание savings-строки оканчивается «(авто)»;
   - у INCOME/EXPENSE строк всё на месте (регрессия: кнопки, чекбокс).
6. **Mutation smoke** (не коммитить порчи): убрать предикат служебности
   → тесты падают; вернуть.
