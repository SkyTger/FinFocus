### 🔴 ПОДТВЕРЖДЁННАЯ РЕГРЕССИЯ: модал профиля не открывается вне дашборда

**Что сломано**: клик по аватару в сайдбаре (`sidebar-profile-container`)
на страницах, отличных от `/dashboard`, не открывает модал профиля.
На дашборде оба входа (аватар и шестерёнка) работают.

**Причина**: `profile_modal.py:97` — добавлен
`Input("dashboard-settings-cog", "n_clicks")` в обычный (серверный)
callback. Элемент шестерёнки рождается динамически внутри
`dashboard-free-header` и существует только на `/dashboard`.
Клиентский рендерер Dash не может разрешить недостающий Input и
**не отправляет callback вовсе** — при этом ошибку в консоль не пишет.
Комментарий в коде (`profile_modal.py:122-123`) утверждает обратное:
«suppress_callback_exceptions снимает риск отсутствия шестерёнки вне
дашборда» — это противоречит уроку, уже задокументированному в памяти
проекта: подавляется только СЕРВЕРНАЯ валидация layout.

**Доказательство (эксперимент, а не рассуждение)**:
- ветка 0028, `/goals`, клик по аватару → **0 запросов** `_dash-update-component`,
  видимых модалов 0, консоль браузера пуста
- `main`, `/goals`, тот же клик → **2 запроса**, модал открыт (1 видимый)
- ветка 0028, `/dashboard`, клик по аватару → модал «Редактировать профиль»
  открывается; клик по шестерёнке → открывается
- Диф `profile_modal.py` содержит ровно одну содержательную правку —
  добавление этого Input'а

**Регрессия задевает функциональность вне scope протокола** (вход в профиль
из сайдбара, протокол 0024) и относится ровно к тому классу дефектов,
который проект уже чинил протоколом 0026.

**Готовое решение в этом же файле**: `dashboard.py:1209-1240` — динамические
кнопки шапки (Сверка, empty-state) идут через `clientside_callback` +
`ClientsideFunction("triggers", "timestamp_trigger")` + Store-триггер.
Шестерёнку нужно перевести на тот же паттерн.
