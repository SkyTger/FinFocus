## Цель

Главный экран должен отвечать на вопрос «сколько у меня реально
свободных денег и что впереди» за 5 секунд. Для этого дашборд получает
шапку-вердикт «Свободно сегодня: N ₽» и график «деньги с именами»
(декомпозиция прогнозного остатка в полосы Свободно / Платежи / Резерв),
построенные на единой сервисной модели данных — она же устраняет
P1-боль UX-аудита 2026-08-20 «цифры соседних карточек противоречат
друг другу».

## Функциональные требования

- **FR-1. Сервисная модель «свободно/платежи/резерв» по дням.**
  Для каждого дня горизонта (текущий календарный месяц, начиная с
  сегодня) модель выдаёт декомпозицию прогнозного остатка на три слоя:
  - *Свободно* — реально доступные деньги;
  - *Платежи* — деньги ещё на счету, но уйдут на уже запланированные
    платежи (регулярные + разовые предстоящие) до конца календарного
    месяца; слой «тает» по мере исполнения платежей и пересчитывается
    на границе месяца;
  - *Резерв* — резерв целей (бюджет накоплений) + подушка.
  Сумма трёх слоёв на день D равна прогнозному остатку на D
  (согласована с балансом кассового календаря). Модель — единый
  источник для шапки, графика и (в куске 2) карточек щитка.
- **FR-2. Шапка-вердикт.** Вверху дашборда: «Свободно сегодня: N ₽»
  (N — срез модели FR-1 на сегодня) + цветовой вердикт состояния
  (порядок / впереди просадка / проблема) + краткий разбор
  «баланс − платежи − резерв». Справа — аватар пользователя и служебная
  иконка настроек. Шапка не является дверью-переходом. Шапка-вердикт
  **заменяет текущий ряд 4 KPI-карточек** (два «главных числа» рядом
  недопустимы — воспроизводят боль противоречия цифр).
- **FR-3. График полос.** Текущий график (grouped bars + линия баланса,
  протокол 0022) заменяется полностью: стопка полос
  Свободно (зелёный) / Платежи (оранжевый) / Резерв (синий) по дням,
  вехи целей на оси времени, вертикальная линия «сегодня», маркер
  минимума остатка. График и шапка — единый визуальный блок: «свободно
  сегодня» есть срез графика на сегодня.
- **FR-4. Тултип-пояснение легенды.** У легенды графика — пояснение с
  конкретикой: для «Платежей» — список предстоящих платежей с датами
  («аренда 25 авг, коммуналка 28 авг…»); для остальных слоёв — что
  входит в слой. Закрывает часть P1-боли «продукт не объясняет себя».
- **FR-5. Пристройство механик вытесняемого KPI-ряда.** Вход в «Сверку»
  с дашборда сохраняется (сейчас — кнопка на KPI-карточке баланса).
  Судьба показателя «Доходы за месяц» решается проектированием явно:
  сохранить в новом месте или убрать осознанно (не потерять молча).
- **FR-6. Пустые состояния.** При нулевых данных (новый пользователь,
  0 операций) шапка и график показывают спроектированное пустое
  состояние: без осей −1..1, склеек подписей и прочих артефактов
  деградации (P2 аудита).

## Нефункциональные требования

- **NFR-1. Производительность.** Загрузка дашборда с новой моделью и
  графиком — не медленнее текущего дашборда; ориентир из метрик
  ROADMAP — < 2 секунд на локальной базе с наполненными данными.
- **NFR-2. Наблюдаемость.** Сбои расчёта модели логируются через loguru
  с трейсбеком (`logger.opt(exception=True)` — идиома проекта,
  протокол 0027), не молча.

## Ограничения

- **C-1.** Остальные разделы (календарь, цели, операции, аналитика) и
  сайдбар в этом куске не трогаются. Таблицы операций, wishlist-виджет
  и карточка подушки на дашборде остаются как есть — их превращение в
  карточки-двери — кусок 2.
- **C-2.** Дисциплина сервисного слоя сохраняется: Decimal для денег,
  session-контракт flush()/commit(), сервисы не знают о Dash
  (KB: `architecture.md`).
- **C-3.** Существующее поведение сервисов не меняется — модель FR-1
  строится надстройкой/композицией; полный прогон тестов (565 на
  2026-08-21) остаётся зелёным.
- **C-4.** Схема БД не меняется (изменение эпиком не заявлено —
  design.md). Если проектирование покажет необходимость — фиксировать
  отдельным решением, не молча.
- **C-5.** Горизонт слоя «Платежи» — до конца календарного месяца
  (принятое решение design.md; платежи начала следующего месяца до
  зарплаты не видны — осознанное ограничение, вспомнить при жалобах
  беты). Механику «основного дохода» не реализовывать.

## Критерии приёмки

- **AC-1.** Дано: наполненная база (операции, регулярки, цели, подушка).
  Когда: открыт дашборд. Тогда: видна шапка «Свободно сегодня: N ₽» с
  цветовым вердиктом и разбором, и N совпадает со значением слоя
  «Свободно» модели на сегодняшнюю дату (срез графика).
- **AC-2.** На дашборде отображается график стопки трёх полос с легендой
  «Свободно / Платежи / Резерв», вехами целей, линией «сегодня» и
  маркером минимума; старый график доходы/расходы+баланс и ряд
  4 KPI-карточек на дашборде отсутствуют.
- **AC-3.** Для любого дня D горизонта сумма трёх слоёв модели равна
  прогнозному остатку на D из кассового календаря
  (CalendarService) — проверено unit-тестом.
- **AC-4.** Наведение/клик на пояснение легенды «Платежи» показывает
  список конкретных предстоящих платежей с датами до конца месяца.
- **AC-5.** Дано: чистая база (онбординг пропущен, 0 операций).
  Когда: открыт дашборд. Тогда: шапка и график показывают осмысленное
  пустое состояние без артефактов (осей −1..1, «50.001k», склеек
  подписей).
- **AC-6.** Вход в сверку с дашборда работает: модал сверки открывается
  и применяется, как до редизайна.
- **AC-7.** Новая модель покрыта unit-тестами (включая границу месяца и
  «таяние» платежей); полный прогон pytest зелёный; black + flake8 без
  новых замечаний.
