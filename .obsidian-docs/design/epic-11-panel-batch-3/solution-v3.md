# Solution v3: Полоска-меню с идентичностью узла через `id` + версия из `app/version.py`

## Обзор решения

Компонент `create_sidebar` заменяется чистой функцией `create_nav_rail(pathname, profile)` в новом модуле `app/components/nav_rail.py`; серверный слот-колбэк `render_sidebar_slot` переименовывается в `render_nav_rail_slot` и остаётся единственным колбэком навигации (те же два Input'а на всегда присутствующие `url` и `profile-updated`).

Ключ к FR-2 — разворот делается CSS-анимацией `@keyframes`, играющей **на монтировании DOM-узла**: при переходе раздел→раздел React-реконсиляция Dash 2.17 переиспользует узел (тип совпадает, **React-ключ обёртки совпадает**), поэтому `animation` не перезапускается; при входе с дашборда слот был пуст (`[]`), узел монтируется заново — разворот играет. Различитель «пришёл с дашборда» — сам факт пустого слота на дашборде, то есть уже существующий механизм C-2, а не второй источник правды. Ни clientside-колбэка, ни хранения предыдущего pathname не требуется — C-1/C-2/C-3 соблюдены буквально.

**Что изменилось против v1 по существу** (три вещи, остальное — точечные правки):

1. **Носитель идентичности узла — `id="nav-rail"` на кожухе, а не `key=`.** Проверка исходников dash-renderer 2.17.1 показала, что React-ключ обёртки берётся из `stringifyId(props.id)`, а проп `key` в этом выражении не участвует вовсе (Ф1). `key=` убран из решения целиком; при отсутствии `id` ключ был бы `undefined` и идентичность держалась бы на позиционном сопоставлении — работающем, но хрупком к любой вставке второго элемента в слот. `id` — штатный механизм Dash сказать «это тот же узел».

2. **Гипотеза о переиспользовании узла проверяется ШАГОМ 0 — на живом сайдбаре, до единого удаления,** и у неё есть записанный план Б (решение владельца Р1): не работает штатными средствами → FR-2/AC-5 выносится в Epic-10, кусок 3 закрывается по остальным десяти AC. Вариант с обработчиком в браузере отвергнут владельцем окончательно.

3. **Зона отсечения перенесена с кожуха на внутреннюю обёртку `.nav-rail-inner`.** Утверждение v1 «`clip-path: inset(0)` не обрезает ничего» фактически неверно: `inset(0)` обрезает ровно по border-box и срезал бы язычок — та самая проблема, от которой уходили отказом от `overflow: hidden`. Кожух и язычок теперь никогда не получают `clip-path`, геометрия одинакова в обоих режимах (обычный и reduced-motion).

Плюс: `app/__version__.py` переименован в `app/version.py` (снят конфликт имени модуля с атрибутом), удаление `sidebar.py` заменено на файл-надгробие (решение владельца Р2), удаление сайдбара переехало в конец плана — после появления `test_nav_rail.py` и после живой проверки AC-5.

## Архитектура

### Компоненты

**1. `app/components/nav_rail.py` (новый) — чистая функция построения полоски**

Ответственности:
- `RAIL_SECTIONS` — четыре раздела (Календарь, Операции, Аналитика, Цели) с `label`, `icon`, `href`. Дашборда в списке НЕТ: на него ведёт логотип (C-6 выполняется, форма другая — пять маршрутов, четыре иконки).
- `create_nav_rail(pathname, profile_data)` → `html.Div(id="nav-rail")` — кожух: внутри `html.Div(className="nav-rail-inner")`, а в нём логотип-домик (`dcc.Link` на `/dashboard`), разделитель, четыре слота-`dcc.Link`, распорка, аватар-`html.Div` с `id="nav-rail-avatar"` и `n_clicks=0`.
- Подсветка активного пункта и текст язычков вычисляются на построении, из аргумента `pathname`. Профиль (эмодзи аватара) — из аргумента `profile_data`.
- В модуле НЕТ `@callback`, НЕТ `get_db_session` — регрессионный якорь.

**Про `id` на кожухе.** `id="nav-rail"` существует ровно для одной цели: дать React стабильный ключ обёртки, чтобы узел переиспользовался между разделами (FR-2). Это **не приглашение вешать на него Input/Output** — такой Output был бы гонкой с `render_nav_rail_slot`, создающим тот же узел (тот же класс регрессий, что протоколы 0026/0028). Инвариант закреплён тестом-якорем: ни `nav-rail`, ни `nav-rail-inner`, ни `nav-rail-avatar` не встречаются в декораторах серверных колбэков; `nav-rail-avatar` допускается только в clientside-триггере `main.py` (C-3).

**Почему новый модуль, а не правка `sidebar.py`:** старое имя врёт о новой сущности — «сайдбар» больше не сайдбар, а `.sidebar-*` CSS весь про 288px-карточку.

**Судьба `app/components/sidebar.py` — файл-надгробие (основной путь, решение владельца Р2).** Файл усыхает до `ADDITIONAL_NAV_ITEMS` плюс докстринг: «остаток удалённого сайдбара; константа сохранена решением владельца 2026-08-27, вернуть иконку при появлении `/settings` или `/help`». Уходят: `MAIN_NAV_ITEMS`, `_build_nav_links`, `create_sidebar`, зашитая `html.Span("v1.0.0")` (строка 166), импорты `dbc`/`html`/`get_avatar_emoji`/`UserProfile`. Удаление файла целиком **отвергнуто владельцем** и в решении не предлагается даже как альтернатива: прецедент «решение владельца можно обойти удачной трактовкой» дороже одного почти пустого файла. Следствие для приёмки: критерий — «нет ни одного **исполняемого** упоминания старого сайдбара (импорт, id, CSS-класс `.sidebar-*`)», а не «нет вхождений строки sidebar».

**2. `app/main.py` — слот-колбэк и clientside-триггер аватара**

- `render_sidebar_slot` → `render_nav_rail_slot`. Контракт входов НЕ меняется: `Input("url", "pathname")`, `Input("profile-updated", "data")`. Логика ветвления та же: `pathname in (None, "/", "/dashboard")` → `[]` до открытия сессии; иначе — сессия, чтение профиля, fail-open на заглушку.
- **Возврат — ровно один компонент, а не список.** Это часть механизма FR-2 (стабильная позиция единственного ребёнка) и фиксируется тестом.
- Слот в layout: `html.Div(id="nav-rail-slot", className="nav-rail-column")` (сейчас `sidebar-slot`/`sidebar-column`, `main.py:75`). Переименование не косметика: старый `.sidebar-column` имеет `width: 288px`.
- Clientside-триггер аватара: `Input("nav-rail-avatar", "n_clicks")` → `Output("open-profile-trigger", "data")` через существующую `ClientsideFunction("triggers", "timestamp_trigger")`. Новой JS-функции не нужно.

**3. `app/version.py` (новый) — единственный источник версии**

```python
__version__ = "0.9.0-beta.1"
```
Имя `version.py`, **не** `__version__.py`: после `from app.version import __version__` в `app/__init__.py` имя `app.__version__` означает строку. Если бы модуль назывался `__version__.py`, то `app.__version__` перекрывал бы ссылку на подмодуль и порядок импортов начал бы влиять на то, что за объект получится. `app/version.py` снимает это за ноль стоимости.

`app/__init__.py` (сейчас ровно 0 байт, Ф3) наполняется реэкспортом. **Инвариант:** в `app/__init__.py` не появляется ничего, кроме докстринга, реэкспорта версии и `__all__`. Причина: файл выполняется при любом `import app.<что угодно>`; через два протокола там окажется импорт сервисов и циклическая зависимость. Инвариант покрывается тестом (`test_app_init_contains_only_version_reexport`).

**Условие попадания в PyInstaller-бандл (называю явно, потому что оно и есть содержание утверждения):** модуль попадает в `PYZ` тогда и только тогда, когда он **достижим по статическому графу импортов от `run.py`**. Достижим он через цепочку `run.py → app.main → app.components.profile_modal → from app import __version__`. Следствие, которое надо знать: если однажды строку версии уберут из модала, модуль молча выпадет из бандла. Поэтому `finfocus.spec` не правится, но факт попадания проверяется **сборкой**, а не рассуждением (чек-лист). Отвергнуты: `importlib.metadata` (проект не устанавливается как дистрибутив — ни `pyproject.toml`, ни `setup.py` нет, `version("finfocus")` → `PackageNotFoundError`); data-файл `VERSION` (потребовал бы `get_bundle_dir()` и явную строку в `datas` спеки); чтение git-тега в рантайме (в бандле нет `.git`).

**4. `app/components/profile_modal.py` — версия в окне профиля (FR-5)**

В `ModalFooter` (строка 62) добавляется `html.Span(f"FinFocus v{__version__}", className="profile-modal-version text-muted small me-auto")` — слева от кнопок. Вычисляется на построении: модал в глобальном layout, присутствует всегда, колбэка не нужно. Существующий `handle_profile_modal` не меняется вовсе.

**5. `app/assets/nav_rail.css` (новый) — геометрия, состояния, разворот**

Колонка `.nav-rail-column` (sticky, 60px, `:empty { display: none }` — ровно одно правило), кожух `.nav-rail` (стекло + `@supports not` fallback, radius 14px, **без `overflow: hidden` и без `clip-path`**), внутренняя обёртка `.nav-rail-inner` (носитель `@keyframes`), логотип, разделитель, слоты, hover, active-пилюля, язычок, аватар, распорка, `@keyframes nav-rail-unfold`, блок `@media (prefers-reduced-motion: reduce)`.

`app/assets/sidebar.css` удаляется целиком (весь про 288px; `.sidebar-card`, `.sidebar-nav-item-active`, `.sidebar-profile*`, `.sidebar-separator`, `.sidebar-column`) — это CSS-файл, а не носитель решения владельца; на него запрет не распространяется.

### Механизм FR-2/AC-5

Разбор четырёх вариантов (сохранён из v1, вариант D переписан).

**Вариант A (выбран): CSS-`animation`, играющая на монтировании узла.**

Приложение — SPA: `dcc.Link` меняет `url.pathname` без перезагрузки, глобальный layout не пересоздаётся. Слот-колбэк отдаёт в `nav-rail-slot.children`:
- дашборд → раздел: `[]` → `Div#nav-rail`. React монтирует новый DOM-узел. `animation`, объявленная на `.nav-rail-inner`, проигрывается — анимациям, в отличие от `transition`, не нужно стартовое значение «от чего интерполировать», у них есть `from` в `@keyframes`.
- раздел → раздел: `Div#nav-rail` → `Div#nav-rail`. Тип элемента и **React-ключ обёртки** совпадают → React переиспользует DOM-узел и лишь патчит атрибуты (`className` активного слота, `aria-current`). Узел не размонтировался → `animation` не перезапускается.
- раздел → дашборд: `Div#nav-rail` → `[]`, узел размонтирован. Следующий вход снова монтирует → разворот сыграет.

**Носитель идентичности — `id`, и вот почему именно он (Ф1).** В dash 2.17.1, `dash-renderer/build/dash_renderer.dev.js`:
- `createContainer` (~3972): `key: component && component.props && stringifyId(component.props.id) || key` — React-ключ обёртки берётся из **`props.id`**; проп `key` в этом выражении не участвует;
- `getChildren` (~4035) **не передаёт четвёртый аргумент** → при отсутствии `id` ключ = `undefined` → React сопоставляет детей по индексу;
- `ErrorBoundary` (~4219): `key: props.id` — то же самое.

Значит `id="nav-rail"` даёт React стабильный именованный ключ обёртки — то самое поведение, которое v1 ошибочно ожидала от `key`. Без `id` механизм тоже сработал бы (один ребёнок, индекс 0, тот же тип `TreeContainer`), но по позиции — и сломался бы, как только в слоте окажется второй элемент (Epic-08 прямо назван в Out of scope как «не блокировать»).

**Оговорка про `key`:** проп `key` на компоненте Dash долетает до внутреннего DOM-элемента как обычный атрибут и на реконсиляцию обёртки не влияет. Кроме того, `dcc.Link` его вообще не принимает: `dcc.Link(href='/a', key='k')` → `TypeError: The dcc.Link component (version 2.17.1) received an unexpected keyword argument: key` (Ф2). В решении `key` не используется нигде.

Что проигрывает вариант A: зависимость от деталей реконсиляции React конкретной сборки. Митигация — не рассуждение, а **шаг 0** (проверка на живом сайдбаре) плюс `id` плюс тест-якорь, фиксирующий предпосылки (R1).

**Вариант B (отвергнут): CSS-`transition` высоты.** Не работает: свежесмонтированный узел не имеет предыдущего вычисленного значения, интерполировать не от чего. Чтобы `transition` сыграл, нужно два кадра — смонтировать в схлопнутом состоянии и в следующем кадре снять класс; снять его может только JS, то есть весь вариант C с его ценой. Спека формулирует FR-2 как «реализация — CSS-переход», но это техническая формулировка требования «средствами CSS, не JS-твинов»; `@keyframes` — тоже CSS и требованию удовлетворяет, при этом единственная CSS-техника, работающая на монтировании. **Отдельного подтверждения владельца это не требует** — аргумент самодостаточен, достаточно записи здесь (снято по замечанию 8).

**Вариант C (отвергнут окончательно, решением владельца): clientside-колбэк, различающий переходы.** Держал бы предыдущий pathname в `dcc.Store` и переключал класс на кожухе. Проигрывает трижды: (1) Output на условно присутствующий элемент — ровно тот класс регрессий, который протокол 0030 запретил Подходом B, и гонка с `render_nav_rail_slot`, создающим тот же узел; (2) хранение предыдущего pathname — второй источник правды о том, «откуда пришли», при том что первый (пустой слот) уже есть; (3) нарушает смысл C-1. **Владелец отверг этот вариант окончательно (Р1)** — проект чинил этот класс регрессий дважды (0026, 0028). В плане Б его нет.

**Вариант D (отвергнут целиком): проп `key=` на компоненте.** В v1 он фигурировал как «страховка от R1». В Dash 2.17 он на реконсиляцию обёртки не влияет (Ф1), а на `dcc.Link` вызывает `TypeError` (Ф2). Убран из компонента, докстрингов, RTM, тестов и таблицы рисков.

**План Б (решение владельца Р1) — порядок обязателен:**

- **Б0 (шаг 0, до любых удалений).** Дешёвая проверка гипотезы на ЖИВОМ сайдбаре: временно добавить в `sidebar.css` `@keyframes __probe { from {opacity:.3} to {opacity:1} }` и `animation: __probe 1s` на `.sidebar-card`; в браузере из `.venv` пройти `/calendar → /goals → /analytics`; наблюдать `animationstart` в DevTools (Event Listener Breakpoints или лог из консоли) и подсветку пересоздания узла в Elements. Моргание на каждом переходе → гипотеза неверна. Правка временная, откатывается сразу после наблюдения; в коммит не попадает.
- **Б1 (если Б0 показал переигрывание).** Штатное средство — стабильный `id` на кожухе: у живого `.sidebar-card` `id` нет, и переигрывание объяснялось бы именно позиционным сопоставлением. Добавить временный `id` в пробу и повторить наблюдение.
- **Б2 (если и с `id` не работает).** Разворот **выносится в Epic-10**, где уже лежит родственная «анимация перехода дашборд↔раздел». `@keyframes` в `nav_rail.css` не добавляются, `.nav-rail-inner` остаётся (он даром), кусок 3 закрывается по остальным десяти AC: AC-1..AC-4, AC-6 (тривиально — анимации нет вовсе), AC-7..AC-11. Отступление фиксируется письменно, как в куске 2 (закрылся с зафиксированным отступлением от FR-1.a). **Решение о переходе к Б2 принимает владелец, по факту наблюдения на шаге 0 или 7′.**

Что решение не делает: не пытается «дожать» механизм ослаблением C-1. Цена «нет разворота» = минус одна анимация. Цена варианта C = нарушение инварианта, который проект дважды чинил регрессиями.

## Обработка ошибок

**Fail-open чтения профиля (наследуется без изменений).** `render_nav_rail_slot` при исключении логирует и подставляет `UserProfile(name="Пользователь", avatar_id=DEFAULT_AVATAR_ID)` — навигация остаётся рабочей, потому что находимость разделов важнее аватара. Существующий тест `TestFailOpenProfile` переносится.

**Битый `avatar_id`.** `get_avatar_emoji` уже возвращает дефолтный эмодзи при неизвестном id — дополнительной защиты не нужно.

**Отсутствующий/битый `pathname`.** `create_nav_rail(None, …)` не падает: `None` и `"/"` нормализуются в `"/dashboard"`, ни один раздел не активен. Функция тотальна, хотя на дашборде и не вызывается (C-5) — тотальность нужна, чтобы будущий вызов из другого места не был ловушкой.

**Неизвестный pathname (404).** Ни один слот не активен, полоска рисуется целиком — пользователь может уйти с 404 в любой раздел или на дашборд. Улучшение против текущего поведения.

**Импорт версии.** `from app import __version__` — если файла нет, приложение не стартует вовсе (`ImportError` на импорте `profile_modal`). Это правильно: молча показывать «неизвестно» — та же болезнь, что зашитая «v1.0.0». Fail-open здесь НЕ применяется сознательно: сбой на этапе импорта детерминирован и ловится тестом, а не пользователем.

**Расхождение версии с git-тегом.** Не ошибка рантайма, а дефект процесса — ловится скипающимся тестом (`git describe --tags --abbrev=0` при наличии `.git` и доступного `git`; `pytest.skip` иначе — в бандле и на машинах без git). Это замена «докстринг просит бампить одновременно», которая митигацией не была.

**Отсутствие `backdrop-filter`.** `@supports not (backdrop-filter: blur(16px))` → `background: rgba(255,255,255,0.92)` — тот же приём, что в `sidebar.css:37-41` / `panel.css`.

**`prefers-reduced-motion: reduce`.** `animation: none` на `.nav-rail-inner`. Важно: обнуляется `animation` целиком, а не только `animation-duration`, иначе `from`-кадр применится и залипнет. Поскольку зона отсечения вынесена на внутреннюю обёртку и используется `fill-mode: backwards`, **геометрия в обоих режимах одинакова**: ни в обычном, ни в reduced-motion на элементах не остаётся `clip-path` после завершения.

## План реализации

Порядок изменён против v1: единственная необратимая операция (удаление сайдбара) отодвинута за живую проверку AC-5, а перед всем поставлена дешёвая проверка гипотезы.

**0. Проверить гипотезу о переиспользовании узла — на ЖИВОМ сайдбаре, до единого удаления (~20 минут). ДВЕ пробы, обязательны обе.**

Из `.venv` проекта (не системного python — там dash 3.2.0, поведение версионно-чувствительно).

Почему двух проб мало одной (замечание 3 критики v2): у живого `.sidebar-card` **нет `id`** (`create_sidebar` возвращает `dbc.Card(className="sidebar-card", ...)`, `sidebar.py:178-180`), а целевая конструкция — `.nav-rail` **с** `id`. По собственной модели решения это два разных режима реконсиляции: без `id` React-ключ обёртки `undefined` → сопоставление по индексу; с `id` → именованный ключ. Проба только в первом режиме не переносится на второй.

- **0.a — контроль (индексное сопоставление).** Временно в `app/assets/sidebar.css`: `@keyframes __probe { from {opacity:.3} to {opacity:1} }` и `animation: __probe 1s` на `.sidebar-card`. В браузере пройти `/calendar → /goals → /analytics`.
- **0.b — целевой режим (именованный ключ).** Та же проба, но на тот же узел временно добавлен `id="__probe-rail"` (правка одной строки в `create_sidebar`). Те же переходы.

В обеих пробах наблюдать: (а) моргает ли карточка на каждом переходе; (б) срабатывает ли `animationstart` (DevTools → Sources → Event Listener Breakpoints → Animation, либо разовый слушатель из консоли); (в) **прямое наблюдение идентичности узла**, не опосредованное анимацией: выделить узел в Elements, запомнить как `$0`, перейти в другой раздел и проверить, что `$0` всё ещё указывает на элемент в документе (`document.contains($0)` → `true`). Это и есть прямой ответ на вопрос «монтируется или патчится».

**Матрица исходов — все три разобраны заранее:**

| 0.a (без `id`) | 0.b (с `id`) | Вывод и действие |

### Уточнение по язычку и зоне отсечения (техническая деталь CSS)

Кожух в эскизе имеет `overflow: hidden` — он нужен и для скругления, и как носитель `max-height`-анимации. Но язычок выходит ЗА пределы кожуха вправо (`left: calc(100% + 9px)` от слота 44px внутри 60px-кожуха) — `overflow: hidden` его обрежет.

v1 уходила от этого через `clip-path` на кожухе с `fill-mode: both` и утверждала, что «после завершения `clip-path: inset(0)` не обрезает ничего». **Это фактически неверно:** `inset(0)` обрезает ровно по border-box, то есть срезал бы язычок постоянно — ровно та проблема, от которой уходили. Плюс `animation: none` в reduced-motion снимал бы `clip-path` вовсе, и геометрия отсечения различалась бы у разных пользователей.

**Выбранное решение (подход C критика):** анимируется **внутренняя обёртка `.nav-rail-inner`**, а кожух `.nav-rail` (фон, граница, тень, скругление) никогда не получает ни `overflow: hidden`, ни `clip-path`. Плюс `fill-mode: backwards` вместо `both`: `from`-кадр применяется до старта, после завершения свойство снимается.

```css
.nav-rail        { border-radius: var(--pnl-radius); height: 100%;
                   /* НЕТ overflow, НЕТ clip-path.
                      height: 100% обязателен: без него процентная высота
                      ребёнка вырождается в auto, и распорка перестаёт
                      прижимать аватар к низу (замечание 4). У прежнего
                      .sidebar-card это стояло явно (sidebar.css:34). */ }
.nav-rail-inner  { display: flex; flex-direction: column; align-items: center;
                   height: 100%; padding: 10px 0 12px;
                   /* backwards, а НЕ both: both оставил бы to-кадр
                      (clip-path: inset(0)) на узле навсегда. Собственного
                      эффекта backwards здесь не имеет — animation-delay
                      нулевой, интервал «до старта» пуст (замечание 5). */
                   animation: nav-rail-unfold 220ms cubic-bezier(.2,.8,.2,1) backwards; }

@keyframes nav-rail-unfold {
  /* Видимая зона кадра 0 = padding-top (10) + логотип (44) = 54px.
     Выражением от тех же переменных, что и остальная геометрия (R7). */
  from { clip-path: inset(0 0 calc(100% - (10px + var(--rail-slot))) 0); opacity: .35; }
  to   { clip-path: inset(0 0 0 0);                                      opacity: 1;   }
}

@media (prefers-reduced-motion: reduce) {
  .nav-rail-inner { animation: none; }
}
```

Итог: `clip-path` не остаётся ни на одном узле после завершения — ни в обычном режиме (`backwards` его снимает), ни в reduced-motion (`animation: none` не даёт ему появиться). **Геометрия в обоих режимах одинакова**, язычок свободно выходит вправо всегда. Расхождение, найденное критиком, устранено конструктивно, а не оговоркой.

**Сверка с эскизом выполнена по исходнику (не отложена на шаг 7′), и она даёт расхождение — решение владельца Р5.** В `.visual/finfocus-panel-rail/v4.html` класс раскадровки `.frame-rail.cut { height: 118px }` / `.cut-2 { height: 186px }` (строки 260-262) применён к `<div class="rail frame-rail cut">`, то есть к `.rail` — узлу, который несёт `background: var(--glass-bg)`, `border`, `border-radius`, `box-shadow`, `padding: 10px 0 12px` и `overflow: hidden` (строки 94-106). Подписи кадров подтверждают: «Кожух схлопнут до высоты знака», «Кожух растёт вниз». То есть в эскизе схлопывается **сама стеклянная плашка**, а не содержимое внутри неё.

**Решение владельца (2026-08-28): подписи важнее буквального роста плашки.** Кожух стоит сразу целиком, содержимое внутри проявляется сверху вниз. Отступление от раскадровки зафиксировано строкой RTM #72 (тип Δ) — прецедент куска 2 (окошко «вчера») действует.

Почему обратный путь закрыт, а не оставлен «на глаз»: `clip-path` на кожухе высоту не меняет — соседи по флексу не сдвинутся, граница и тень будут срезаться линией отсечения вместо скругления по уменьшенному прямоугольнику, то есть кадр эскиза всё равно не воспроизводится. Единственный способ получить рост плашки — `max-height` + `overflow: hidden` на кожухе, а это возвращает обрезку язычка, снятую правкой №6, причём уже неустранимую переносом на обёртку (обрезает контейнер, а не clip). Все известные обходы (вынос язычка через `position: fixed` с координатами от JS; дублирование через `::after` на кожухе, не дающее разных подписей четырём слотам) тянут за собой обработчик в браузере — то есть вариант C, отвергнутый владельцем в Р1. Развилки на шаге 7′ больше нет: путь выбран здесь.

## Ответы на вопросы критика

**[факт] 1. Читалась ли раскадровка по исходнику эскиза до того, как сверка была отложена на шаг 7′?** Нет — и критик прав, что это следовало сделать сразу. Сверка выполнена сейчас, оркестратором, по исходнику: `.frame-rail.cut { height: 118px }` и `.cut-2 { height: 186px }` (строки 260-262) применены к `<div class="rail frame-rail cut">`, то есть к `.rail` — узлу с `background: var(--glass-bg)`, `border`, `border-radius`, `box-shadow`, `padding: 10px 0 12px` и `overflow: hidden` (строки 94-106). Подписи кадров подтверждают трактовку дословно. Расхождение с конструкцией v2 реально: там кожух не трогается вовсе. **Следствие для v3:** вопрос вынесен владельцу и закрыт решением Р5, отступление зафиксировано RTM #72, развилка с шага 7′ снята.

**[факт] 2. Откуда число 64 в `calc(100% - 64px)`?** Из ошибочного сложения: RTM #60 v2 раскладывала его как «44 + 10 + 10», сложив верхний отступ дважды. Фактически `padding` у `.nav-rail-inner` — `10px 0 12px`: верхний отступ один (10), нижний находится у противоположного края и в видимую сверху зону войти не может. **Целевое число — 54px** (`padding-top` + логотип), и оно записано не числом, а выражением `calc(100% - (10px + var(--rail-slot)))`. 118px эскиза — третье число из другого механизма (схлопывание кожуха), отвергнутого в Р5, и в конструкцию с `clip-path` не переносится.

**[факт] 3. Есть ли у `.nav-rail` явная высота?** В v2 не было — критик прав, это дефект. В перечне свойств кожуха стояли фон, граница, скругление и тень, при этом `.nav-rail-inner` объявлялся с `height: 100%`, который без высоты родителя вырождается в `auto`. **Следствие для v3:** `height: 100%` дописан кожуху в CSS-блоке и в RTM #55, с указанием цены ошибки (распорка перестаёт работать) и прецедента (`sidebar.css:34`).

**[факт] 4. Что докажет шаг 0, если проба на `.sidebar-card` (узел без `id`) не моргнёт?** В формулировке v2 — только то, что индексное сопоставление работает при одном ребёнке; на целевой режим с именованным ключом это не переносится, и критик прав, что это та же ложная уверенность, за которую v1 получила блокер. **Следствие для v3:** шаг 0 разбит на две обязательные пробы (без `id` / с `id`) с матрицей всех трёх исходов и прямым наблюдением идентичности узла через `$0`/`document.contains($0)`, не опосредованным анимацией.

**[решение] 5. Если сверка подтвердит расхождение — фиксируем отступление письменно или разворот уходит в Epic-10 вместе с Б2?** **Решение владельца Р5 (2026-08-28): фиксируем отступление письменно, разворот остаётся в куске 3.** Выбор сделан в пользу подписей: они выходят за правую границу кожуха, а рост плашки требует обрезки по её краю и срезал бы их постоянно — при 60px-полоске подписи вместе с `aria-label` несут всю смысловую нагрузку иконок (NFR-4 прямо запрещает подписи быть единственным носителем, значит она обязана быть одним из двух). Отступление зафиксировано RTM #72 типа Δ по образцу куска 2. Б2 (вынос в Epic-10) остаётся планом Б **только** для случая, когда шаг 0 покажет неработоспособность самого механизма переиспользования узла, — это другое основание, не раскадровка.
