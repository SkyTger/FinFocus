## 🔴 Критичные проблемы (Blockers)

### 1. `key="nav-rail"` не работает так, как заявлено — страховка R1 фиктивна, а часть путей ведёт к ошибке импорта

**Где:**
- Solution, «Вариант D (отвергнут как механизм, принят как страховка)»
- Solution, докстринг `create_nav_rail`: «совпадают тип, позиция и **ключ**»
- Solution, RTM #8; шаг 4 плана; тест `TestNavRailStructureStable`; риск R1

**Проблема:**
Проверены исходники dash-renderer в `.venv/lib/python3.10/site-packages/dash/dash-renderer/build/dash_renderer.dev.js` (dash 2.17.1). Механика построения детей:

```js
// createContainer, строка ~3969-3978
value: function createContainer(props, component, path) {
  var key = arguments.length > 3 && arguments[3] !== undefined ? arguments[3] : undefined;
  return isSimpleComponent(component) ? component : React.createElement(TreeContainer, {
    key: component && component.props && stringifyId(component.props.id) || key,
    ...
  });
}

// getChildren, строка ~4030-4037
return Array.isArray(components)
  ? addIndex(map)(function (component, i) {
      return _this2.createContainer(_this2.props, component, append(path, ['props','children', i]));
                                                          // ← ЧЕТВЁРТОГО аргумента НЕТ
    }, components)
  : this.createContainer(this.props, components, append(path, ['props','children']));
```

Три следствия:

**(а) React-ключ обёртки берётся из `props.id`, а не из `props.key`.** Проп `key`, который архитектор ставит на `html.Div`, в этом выражении **не участвует вообще**. Он уходит в `props` и попадает на внутренний DOM-элемент (`getComponent` → `createElement(element, allProps, children)`, строка ~3946). Заявление «явный `key="nav-rail"` явно фиксирует "это тот же узел"» **неверно для Dash 2.17**.

**(б) У кожуха нет `id`, значит ключ — `undefined`, и идентичность держится на позиции.** В решении `.nav-rail` описан как `html.Div(className="nav-rail", key="nav-rail")` — без `id`. Значит `stringifyId(props.id)` даёт `undefined`, четвёртый аргумент тоже `undefined`, и React сопоставляет детей **по индексу**. Механизм фактически сработает (один ребёнок, индекс 0, тот же тип `TreeContainer`), но по другой причине, чем написано — и причина хрупкая.

**(в) `dcc.Link` вообще не принимает `key`.** В `dash/dcc/Link.py` пропа `key` в `_prop_names` нет; у `html.Div` есть. Если реализатор применит «страховку `key=`» к слотам-`dcc.Link` (шаг 4 плана перечисляет их рядом), получит `TypeError` на построении.

**Почему критично:**
Решение объявляет `key` **митигацией риска R1** — единственной технической защитой центрального механизма. Митигация, которой физически нет, хуже честного отсутствия: она снимает бдительность. Реализатор напишет `key="nav-rail"`, тест `TestNavRailStructureStable` позеленеет (проп на компоненте есть), R1 будет считаться закрытым. Реальная защита (стабильная позиция единственного ребёнка) нигде не сформулирована и ничем не проверяется.

**Пример сценария:**
```
Кто-то в Epic-08 (мобильная адаптация — прямо назван в Out of scope
как «не блокировать») добавляет в слот второй элемент:
  return [create_nav_rail(...), create_bottom_bar(...)]  # 2 ребёнка
→ ключи по-прежнему undefined → сопоставление по индексу
→ на узких экранах порядок меняется медиазапросом-логикой
→ React пересоздаёт узел → разворот играет на каждом переходе
→ TestNavRailStructureStable зелёный (верхний узел create_nav_rail не менялся)
```

**Рекомендация:**
1. Убрать `key=` из решения полностью — из `create_nav_rail`, докстринга, RTM #8 и теста.
2. Заменить настоящей страховкой: дать кожуху **`id="nav-rail"`**. Тогда `stringifyId(props.id)` вернёт `"nav-rail"`, React получит стабильный именованный ключ обёртки — ровно то поведение, которое архитектор хотел от `key`.
   Оговорка: `id` на компоненте — не приглашение вешать Input/Output. C-1/C-3 остаются, тест-якорь должен это проверять.
3. В RTM #8 переписать обоснование: «React-ключ обёртки = `stringifyId(props.id)`; кожух несёт `id="nav-rail"`, поэтому ключ стабилен независимо от pathname».
4. В шаге 4 плана явно написать, что `id` ставится **только** на `html.Div` кожуха, а `dcc.Link` пропа `key` не имеет.

### 5. `app/__version__.py` + реэкспорт — имя и импорт создают ловушку

**Где:** Solution, компонент 3, «Ключевые интерфейсы», RTM #16, R3, Blast Radius.

**(а) Имя `__version__.py` конфликтует с атрибутом.** После `from app.__version__ import __version__` в `app/__init__.py` имя `app.__version__` означает **строку**, перекрывая ссылку на подмодуль. Работает, но создаёт неочевидное поведение: `import app.__version__; app.__version__` → строка, не модуль; порядок импортов начинает влиять. Обходится тривиально: `app/version.py`. Решение выбрало самое конфликтное из возможных имён и нигде это не отметило.

**(б) Наполнение `app/__init__.py` меняет стоимость импорта пакета.** Сейчас файл пуст (проверено). После правки любой `import app.<что угодно>` выполнит `__init__.py`. Для одной константы безобидно, но нужен явный инвариант «в `app/__init__.py` не появляется ничего, кроме реэкспорта версии» — иначе через два протокола там окажется импорт сервисов и циклическая зависимость.

**(в) Утверждение про PyInstaller подано как установленное, хотя условие не названо.** «`finfocus.spec` — изменять не требуется: попадает в бандл через `Analysis(["run.py"])`» верно только если модуль **достижим по статическому графу импортов** от `run.py`. Он достижим — через `profile_modal` → `from app import __version__`. Но условие нигде не названо, а именно оно и есть содержание утверждения.

Отдельно: grep `finfocus.spec` на `version|__version__|0.9.0|VERSION` — совпадений нет. Версия в спеке PyInstaller не фигурирует, рассинхрон становится трёхсторонним, а не двухсторонним, как в R3.

**Почему важно:**
FR-5/AC-9 требует, чтобы версия «совпадала с реальной версией проекта». Ручной бамп в двух-трёх местах гарантирует, что рано или поздно не совпадёт — тот же дефект P3, который кусок 3 закрывает. Митигация «в докстринге написано бампить одновременно» — это не митигация, это надежда.

**Рекомендация:**
1. Переименовать в `app/version.py` — снимает (а), ноль стоимости.
2. Записать инвариант содержимого `app/__init__.py` и покрыть тестом.
3. В R3 заменить «докстринг просит» на скипающийся тест: при наличии `.git` сверяет `__version__` с `git describe --tags --abbrev=0`, скипается если git недоступен. ~10 строк, ловит рассинхрон в момент тега, без правки `build.yml`.
4. Явно записать условие достижимости модуля для PyInstaller — чтобы будущее удаление строки версии из модала не унесло модуль из бандла молча.

### 6. Анимация с `both` + `clip-path`: конечное состояние и reduced-motion разобраны неполно

**Где:** Solution, «Уточнение по язычку», «Обработка ошибок», RTM #18, #59-61.

**(а) `both` держит `clip-path: inset(0)` на узле навсегда** — как постоянно применённое значение из `to`-кадра. `clip-path: inset(0)` **обрезает по border-box**. Для язычка, выходящего за правую границу кожуха на `calc(100% + 9px)`, это **та же проблема, от которой уходили через отказ от `overflow: hidden`**. `inset(0)` — не «не обрезает ничего», это «обрезает ровно по границе элемента».
Решение прямо пишет обратное: «после завершения анимации `clip-path` — `inset(0)`, то есть не обрезает ничего». Это фактически неверно и ломает AC-3 в обычном сценарии, не в краевом.

**(б) `animation: none` при reduced-motion снимает и `both`.** Если `clip-path` объявлен только внутри `@keyframes`, при `animation: none` элемент останется без `clip-path` — что хорошо (нет обрезки). Но тогда **два режима дают разную геометрию отсечения**: обычный — с постоянным `inset(0)`, reduced-motion — без `clip-path` вовсе. Язычок будет обрезан у одних пользователей и не обрезан у других. Расхождение не замечено.

**Почему важно:**

## 🔄 Альтернативные подходы

### Подход A: Идентичность узла через `id`, а не через `key` (исправление)
React-ключ обёртки = `stringifyId(component.props.id)` (`createContainer`, ~3972), поэтому именно `id` — штатный механизм Dash сказать «это тот же узел».
**Плюсы:** работает по факту, а не по предположению; снимает зависимость от позиционного сопоставления (устойчиво к Epic-08); ноль стоимости, C-1/C-2/C-3 не затрагиваются.
**Минусы:** `id` выглядит приглашением повесить колбэк — прикрыть тестом-якорем.
**Рекомендация:** взять как основу вместо `key=`.

### Подход B: Разворот как отделяемый инкремент (план Б для AC-5)
Разворот реализуется последним и объявляется отделяемым: не работает механизм — `@keyframes` не добавляются, FR-2/AC-5 переносится в Epic-10, кусок 3 закрывается по остальным десяти AC.
**Плюсы:** убирает точку, где кусок застревает между «сайдбар удалён» и «полоска не соответствует AC»; соответствует стилю эпика (кусок 2 закрылся с зафиксированным отступлением от FR-1.a по решению владельца — прецедент есть); не требует ослаблять C-1.
**Минусы:** AC-5 не выполнен в куске 3 — нужно решение владельца.
**Почему лучше:** цена «нет разворота» = минус одна анимация. Цена «застряли на варианте C» = нарушение инварианта 0030, который проект дважды чинил регрессиями.

### Подход C: Анимировать внутреннюю обёртку, а не кожух (для проблемы 6)
`@keyframes` вешается на `.nav-rail-inner`, кожух (фон, граница, тень) никогда не получает `clip-path`.
**Плюсы:** язычок выходит за границы свободно в обоих режимах — расхождение геометрии исчезает; визуально разворот тот же; снимает вопрос про `fill-mode`.
**Минусы:** лишний узел; если нужно схлопывание самого фона — эффект другой, сверить с раскадровкой эскиза (`v4.html`, блок 3).
