# Solution v1: Полоска-меню на React-реконсиляции + версия из `app/__version__.py`

## Обзор решения

Компонент `create_sidebar` заменяется чистой функцией `create_nav_rail(pathname, profile)` в новом модуле `app/components/nav_rail.py`; серверный слот-колбэк `render_sidebar_slot` переименовывается в `render_nav_rail_slot` и остаётся единственным колбэком навигации (те же два Input'а на всегда присутствующие `url` и `profile-updated`). Ключ к FR-2 — **разворот делается CSS-анимацией `@keyframes`, а не переходом**: React-реконсиляция Dash 2.17 переиспользует DOM-узел кожуха при переходах раздел→раздел (тип элемента и позиция в дереве совпадают, меняются только props), поэтому `animation` проигрывается ровно один раз — на монтировании узла, то есть только при входе с дашборда, где `sidebar-slot` был пуст. Никакого признака предыдущего pathname, никакого clientside-колбэка и никакого второго механизма видимости не требуется — C-1/C-2 соблюдены буквально. Версия заводится как единственный источник правды `app/__version__.py` (константа в питон-модуле, а не файл данных) — она попадает в PyInstaller-бандл вместе с кодом и читается импортом, без обращения к диску.

## Архитектура

### Компоненты

**1. `app/components/nav_rail.py` (новый) — чистая функция построения полоски**

Заменяет `app/components/sidebar.py`. Ответственности:
- `RAIL_SECTIONS` — четыре раздела (Календарь, Операции, Аналитика, Цели) с `label`, `icon`, `href`. Дашборда в списке НЕТ: на него ведёт логотип (C-6 выполняется, но форма другая — пять маршрутов, четыре иконки).
- `create_nav_rail(pathname, profile_data)` → `html.Div` — кожух полоски: логотип-домик (`dcc.Link` на `/dashboard`), разделитель, четыре слота-`dcc.Link`, распорка, аватар-`html.Div` с `id="nav-rail-avatar"` и `n_clicks=0`.
- Подсветка активного пункта и текст язычка вычисляются на построении, из аргумента `pathname`. Профиль (эмодзи аватара) — из аргумента `profile_data`.
- В модуле НЕТ `@callback`, НЕТ `get_db_session` — регрессионный якорь.

Почему **новый модуль**, а не правка `sidebar.py`: (а) старое имя врёт о новой сущности — «сайдбар» больше не сайдбар; (б) `ADDITIONAL_NAV_ITEMS` по решению владельца не трогается, и удобнее оставить `sidebar.py` нетронутым файлом-надгробием, чем половину его переписать. **Однако** оставлять оба модуля — второй источник правды о навигации. Решение: `app/components/sidebar.py` **удаляется целиком** вместе с `ADDITIONAL_NAV_ITEMS` внутри него — это не «трогание константы» (её не переносят, не переименовывают, не оживляют), а удаление файла, который перестал существовать как сущность. Если владелец предпочтёт буквальное «не трогать», альтернатива — оставить `sidebar.py` с одной только константой; это решение владельца, а не архитектора, и вынесено в риски (R4).

**2. `app/main.py` — слот-колбэк и clientside-триггер аватара**

- `render_sidebar_slot` → `render_nav_rail_slot`. Контракт входов НЕ меняется: `Input("url", "pathname")`, `Input("profile-updated", "data")`. Логика ветвления та же: `pathname in (None, "/", "/dashboard")` → `[]` до открытия сессии; иначе — сессия, чтение профиля, fail-open на заглушку.
- Слот в layout: `html.Div(id="nav-rail-slot", className="nav-rail-column")`. Переименование id и класса — не косметика: старый `.sidebar-column` имел `width: 288px`, новый — `60px`, и держать оба под одним именем нельзя без правки старого CSS-файла, который весь про 288px.
- Clientside-триггер аватара: `Input("nav-rail-avatar", "n_clicks")` → `Output("open-profile-trigger", "data")` через существующую `ClientsideFunction("triggers", "timestamp_trigger")`. Новой JS-функции не нужно.

### Механизм FR-2/AC-5 — почему `animation` на монтировании, а не переход

Разбор четырёх вариантов.

**Вариант A (выбран): CSS-`animation` на кожухе, играющая на монтировании узла.**

Приложение — SPA: `dcc.Link` меняет `url.pathname` без перезагрузки страницы, глобальный layout не пересоздаётся. Слот-колбэк отдаёт в `nav-rail-slot.children`:
- дашборд → раздел: `[]` → `[Div.nav-rail]`. React монтирует новый DOM-узел. CSS-`animation`, объявленная на `.nav-rail`, проигрывается — анимации, в отличие от `transition`, не нужно стартовое значение «от чего интерполировать», у них есть `from` в `@keyframes`.
- раздел → раздел: `[Div.nav-rail]` → `[Div.nav-rail]`. Тип элемента и позиция в списке children совпадают, React **переиспользует** существующий DOM-узел и лишь патчит атрибуты (`className` активного слота, `aria-current`). Узел не размонтировался → `animation` не перезапускается. Разворот не переигрывается.
- раздел → дашборд: `[Div.nav-rail]` → `[]`, узел размонтирован. Следующий вход с дашборда снова монтирует → разворот сыграет.

То есть **различитель «пришёл с дашборда» vs «между разделами» — это сам факт того, что на дашборде слот пуст**. Никакого дополнительного признака предыдущего pathname хранить не надо: состояние уже есть в DOM, и оно единственное. Это то же свойство `:empty`, на котором стоит C-2, использованное второй раз — не второй механизм, а следствие первого.

Что проигрывает вариант A: **зависимость от деталей реконсиляции React.** Если структура children слота при переходах раздел→раздел изменится по типу верхнего элемента (например, кто-то обернёт полоску в `dbc.Card` только на одном разделе), React размонтирует узел и разворот сыграет лишний раз. Митигируется тестом, фиксирующим, что верхний элемент дерева `create_nav_rail` — всегда `html.Div` с одним и тем же `className` и `id` независимо от pathname (R1). Второе: если Dash когда-нибудь начнёт присваивать children-узлам ключи, зависящие от контента, узел начнёт пересоздаваться. В Dash 2.17 (пин `requirements.txt`) этого нет; локальный venv это подтверждает.

**Вариант B (отвергнут): CSS-`transition` высоты.** Не работает: свежесмонтированный узел не имеет предыдущего вычисленного значения, интерполировать не от чего. Чтобы `transition` сыграл, нужно два кадра — сначала смонтировать в схлопнутом состоянии, затем в следующем кадре снять класс. Снять его может только JS (`requestAnimationFrame` + `classList`), то есть либо clientside-колбэк, либо MutationObserver — то есть весь вариант C с его ценой. Спека формулирует FR-2 как «реализация — CSS-переход», но это техническая формулировка требования «анимация средствами CSS, не JS-твинов»; `@keyframes` — тоже CSS и требованию удовлетворяет, при этом единственная CSS-техника, которая на монтировании работает вообще. Это единственное место, где решение расходится с буквой спеки, и оно должно быть подтверждено владельцем (R2).

**Вариант C (отвергнут): clientside-колбэк вне компонента, различающий переходы.** Держал бы предыдущий pathname в `dcc.Store` и переключал класс `nav-rail--unfold` на кожухе. Проигрывает трижды: (1) `Output` на класс кожуха — это Output на условно присутствующий элемент, ровно тот класс регрессий, который протокол 0030 запретил Подходом B, и гонка с `render_nav_rail_slot`, который тот же узел в тот же момент создаёт; (2) хранение предыдущего pathname — второй источник правды о том, «откуда пришли», при том что первый (пустой слот) уже есть; (3) даже будучи clientside, колбэк C-1 формально не нарушает (он не в модуле компонента), но нарушает его смысл — «всё, что нужно полоске, приходит аргументами и вычисляется на построении».

**Вариант D (отвергнут как механизм, принят как страховка): ключ узла (`key=`).** Обратная задача: ключ нужен, чтобы узел ПЕРЕСОЗДАВАЛСЯ, а нам нужно наоборот — чтобы он переиспользовался. Полезен как страховка от риска R1 (стабильный `key="nav-rail"` явно фиксирует «это тот же узел») — включён в решение именно в этой роли, не как механизм анимации.

## Модель данных

Схемы БД, миграций и внешних API кусок не трогает (подтверждено осадком решений). Структуры данных:

```python
class RailSection(TypedDict):
    """Раздел полоски."""
    label: str   # подпись язычка, она же aria-label: «Календарь» …
    icon: str    # класс Bootstrap Icons: "bi-calendar3" …
    href: str    # маршрут: "/calendar" …
```

Существующий `UserProfile` (`app/schema/onboarding.py`) используется без изменений; из него берётся только `avatar_id`. Поле `name` в полоске не отображается (не влезает в 60px) — это осознанная потеря по сравнению с сайдбаром, компенсируемая тем, что имя видно в окне профиля, куда ведёт тот же аватар.

Версия — простая строка `str` в модуле `app/__version__.py`; формат — PEP 440-совместимый без префикса `v` (`"0.9.0-beta.1"`), префикс `v` добавляется на отображении и в git-теге.

## Обработка ошибок

**Fail-open чтения профиля (наследуется без изменений).** `render_nav_rail_slot` при исключении логирует и подставляет `UserProfile(name="Пользователь", avatar_id=DEFAULT_AVATAR_ID)` — навигация остаётся рабочей, потому что находимость разделов важнее аватара. Существующий тест `TestFailOpenProfile` переносится.

**Битый `avatar_id`.** `get_avatar_emoji` уже возвращает дефолтный эмодзи при неизвестном id — дополнительной защиты не нужно.

**Отсутствующий/битый `pathname`.** `create_nav_rail(None, …)` не падает: `None` и `"/"` нормализуются в `"/dashboard"`, ни один раздел не активен. Функция тотальна, хотя на дашборде и не вызывается (C-5) — тотальность нужна, чтобы будущий вызов из другого места не был ловушкой.

**Неизвестный pathname (404).** Ни один слот не активен, полоска рисуется целиком — пользователь может уйти с 404 в любой раздел или на дашборд. Это улучшение против текущего поведения.

**Импорт версии.** `from app import __version__` — если файл каким-то образом отсутствует, приложение не стартует вообще (ImportError на импорте `profile_modal`). Это правильно: молча показывать «неизвестно» вместо версии — та же болезнь, что зашитая «v1.0.0». Fail-open здесь НЕ применяется сознательно: сбой на этапе импорта детерминирован и ловится тестом, а не пользователем.

**Отсутствие `backdrop-filter`.** `@supports not (backdrop-filter: blur(16px))` → `background: rgba(255,255,255,0.92)` — тот же приём, что в `sidebar.css`/`panel.css`.

**`prefers-reduced-motion: reduce`.** `animation: none` на `.nav-rail` — полоска сразу в конечном состоянии. Важно: обнулять надо `animation`, а не только `animation-duration`, иначе `from`-кадр применится и залипнет.

## Зависимости

**Новых библиотек не требуется.** Bootstrap Icons уже подключены (`dbc.icons.BOOTSTRAP` в `app/main.py`), `bi-house-door` входит в набор. Язычок-подпись делается чистым CSS (`:hover` + абсолютное позиционирование + `::before`-носик), а не tooltip-компонентом `dbc.Tooltip` — последний потребовал бы `target`-привязку к id каждого слота и добавил бы узлы, живущие вне полоски. Анимация — чистый CSS `@keyframes`, JS-твинов нет. Новая JS-функция в `clientside_triggers.js` не нужна: аватар переиспользует существующую `timestamp_trigger`.

### Уточнение по язычку (техническая деталь, влияющая на CSS)

Кожух полоски в эскизе имеет `overflow: hidden` — он нужен и для скругления, и как носитель анимации `max-height`. Но язычок должен выходить ЗА пределы кожуха вправо (`left: calc(100% + 9px)` от слота шириной 44px внутри 60px-кожуха) — `overflow: hidden` его обрежет.

**Выбранное решение**: анимируется НЕ `max-height` кожуха с `overflow: hidden`, а `clip-path: inset(0 0 N% 0)` на кожухе. Он даёт «разворот сверху вниз» без `overflow`, не влияет на layout и не мешает язычку: после завершения анимации `clip-path` — `inset(0)`, то есть не обрезает ничего, а во время анимации язычок и так не показывается (курсор ещё не на слоте).

```css
@keyframes nav-rail-unfold {
  from { clip-path: inset(0 0 calc(100% - 64px) 0); opacity: .35; }
  to   { clip-path: inset(0 0 0 0);                 opacity: 1;   }
}
.nav-rail { animation: nav-rail-unfold 220ms cubic-bezier(.2,.8,.2,1) both; }
```

`clip-path` анимируется всеми целевыми браузерами, `both` фиксирует конечное состояние. `overflow: hidden` на кожухе становится не нужен вовсе (скругление обеспечивает `border-radius`), и язычок свободно выходит вправо. Это лучше `max-height` и по существу: `max-height` заставлял бы содержимое кожуха переливаться (аватар «доезжал» бы снизу), а раскадровка эскиза показывает именно обрезку — на кадре 110 мс аватара не видно, а не «аватар в середине».
