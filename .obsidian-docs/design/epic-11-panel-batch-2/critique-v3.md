Но конструктор не проверила. `AllocationService` **не определяет `__init__` вообще**: в файле нет ни одного `def __init__`, класс не хранит сессию и работает исключительно с переданным списком ORM-объектов. Заодно поправить строку «Зависимости» и стратегию загрузки: `AllocationService` там числится наравне с session-сервисами. ### 2. `goals_part[yday]` 1-го числа считается по чужому месяцу — резерв «вчера» будет неверным

**Где:**
- solution-v3, п. 2 обзора и таблица хелперов: «`_goals_part_by_day` от состава списка НЕ зависит… `calc_dates` для него безвреден»
- `_yesterday_slice`: `reserve_configured = cushion_threshold + goals_part.get(yday, Decimal("0"))`
- Факт: `money_layers_service.py:578-597`

**Проблема:**
Утверждение «от состава списка не зависит» верно — я проверил, значение каждого ключа есть функция только от `day` и `savings_by_date`. Но из этого не следует, что значение **для ключа `yday`** осмысленно. Тело берёт месяц **по самому дню**:

```python
for day in window_dates:
    month_start = _month_start(day)
    month_end   = _month_end(day)
    ...
    for op_date, amount in savings_by_date.items():
        if month_start <= op_date <= day:      consumed  += amount
        elif day < op_date <= month_end:       committed += amount
    result[day] = max(0, monthly_budget - consumed - committed)
```

В штатном случае (`ref` — не 1-е число) `yday` в том же месяце, что `ref`, и всё сходится. Но когда `ref` = 1-е число, `yday` — последний день **предыдущего** месяца, и тогда для ключа `yday`:
- `month_start`/`month_end` — границы **прошлого** месяца;
- `consumed(yday)` = savings-операции за весь прошлый месяц — а `savings_by_date` собран от `collect_start = min(_month_start(ref), yday)`, то есть содержит **ровно один день** прошлого месяца (сам `yday`), остальные 30 дней не собраны;
- `committed(yday)` = `Σ` по `(yday, month_end(yday)]` = пусто, потому что `yday` и есть `month_end(yday)`;
- итог: `goals_part[yday] = max(0, monthly_budget − savings(yday))` — то есть **полный бюджет текущей настройки минус операции одного дня**, отнесённый к прошлому месяцу, в котором взносы могли быть уже полностью сделаны.

Практическое следствие: 1-го числа окошко «Вчера» покажет резерв ≈ полный месячный бюджет и, соответственно, заниженное «Свободно», хотя за прошлый месяц бюджет мог быть исчерпан. Направление безопасное (занижаем свободное), но цифра неверна и, главное, посчитана **по другому месяцу**, чем соседнее окошко «Сегодня» — то есть ровно «два соседних числа по разной логике», от чего лечит FR-6.

Это не дефект `_goals_part_by_day`: функция написана для окна, целиком лежащего от `ref` вправо, и её собственный докстринг это фиксирует прямым текстом (`:507-511`: «Прошлые месяцы в окно не попадают… поэтому `month_start(D) >= collect_start` для всех D окна, КРОМЕ вырожденного случая `reference_date == 1-е число`, где они совпадают»). `calc_dates` добавляет ключ, для которого эта посылка нарушена — и именно этот случай докстринг уже называет вырожденным.

**Почему важно:**
v3 объявила перечень границ исправленным и покрыла случай «1-е число» тестом — но тест (шаг 1, п. 8) сформулирован как ««вчера» видит операции прошлого месяца (`collect_start`)», то есть проверяет `forecast_balance`, а не `reserve`. Дефект пройдёт мимо него так же, как дефект блокера №1 v2 проходил мимо инварианта. Достижимость — один день в месяц у любого пользователя с настроенным бюджетом целей, то есть заметно шире, чем у принятой в №3 зависимости `_is_empty`.

**Рекомендация:**
Выбрать явно и записать, а не оставить неявным:
- **дешёвый и, по-моему, правильный вариант**: для `yday` не брать `goals_part` вообще, когда `_month_start(ref) > yday` (то есть `ref` — 1-е число), а использовать `goals_part[ref]` — «резерв, настроенный на начало текущего месяца»; либо честно вернуть `yesterday = None` в этот единственный день, и окошко нарисует прочерк (механизм прочерка уже есть и уже описан);
- альтернатива: не добавлять `yday` в `calc_dates` для `_goals_part_by_day` (передавать ему `window_dates`, как сегодня) и брать `goals_part.get(ref)` для «вчера» — тогда единственность списка теряется, зато исчезает ключ с нарушенной посылкой.

В любом случае нужен тест **на значение** `yesterday["reserve_configured"]` на фикстуре «`ref` = 1-е число + savings-операции в прошлом месяце» — симметрично тому, что сделано для `payments`. И строку в таблице границ: `_goals_part_by_day` — «тело без изменений, но ключ `yday` вырожден 1-го числа».

## 🟢 Незначительные замечания (Optional)

### 4. Ветка ошибки `load_and_navigate_calendar` возвращает `state` без изменений — `focus_applied_ts` не запишется

`except Exception` (`:938-948`) возвращает исходный `state` четвёртым элементом. Если фокус пришёл, а загрузка данных упала, `focus_applied_ts` не сохранится, и при следующем срабатывании по любому Input'у первое условие (`ctx.triggered_id == Store`) уже не выполнится — то есть переприменения не будет, поведение безопасное. Стоит одной строкой сказать, что это осознанно (иначе при реализации возникнет соблазн «дописать ts и в ветку ошибки», что как раз вернёт риск).

### 5. `_empty_goals()` в решении используется, но нигде не описан

Функция появляется в двух местах кода (`_goals_block`) и в таблице ошибок, но её контракт не задан: какие значения у `cushion_progress: float`, `others_summary: str`, `top_goal_progress: float` при `EMPTY`. Поскольку `GoalsCardData` объявляет эти поля необязательными-по-смыслу, но обязательными-по-типу (`float`, `str`, не `| None`), реализация обязана положить туда `0.0` и `""` — а тест AC-5 «нет `₽`/`%`» проверяет только дерево, не данные. Одна строка в докстринге `_empty_goals` снимет двусмысленность; тот же вопрос к `_empty_*` для остальных четырёх блоков, если они появятся.

### 6. RTM #62: подпись окошка «вчера» обоснована через `payments`, но `operations_note` для «вчера» останется пустым и на наполненной базе

Эскиз ставил там `&nbsp;`, так что формально всё по эскизу; просто стоит проверить на живой базе, что это не читается как ложное утверждение, и при необходимости убрать место под подпись у «вчера» совсем (а не оставлять пустое).

## 🔄 Альтернативные подходы

По №2 предпочтительный вариант — не расширять `calc_dates` для `_goals_part_by_day`, а взять для «вчера» `goals_part[ref]`:

**Идея:** `_payments_tail_by_day` получает `calc_dates` (ему ключ `yday` нужен и корректен), `_goals_part_by_day` остаётся на `window_dates`, а `_yesterday_slice` использует `goals_part[ref]` как «резерв, настроенный на начало периода».

**Плюсы:** ключа с нарушенной посылкой не возникает вовсе; вырожденный случай 1-го числа исчезает без ветвления по датам; докстринг `_goals_part_by_day` (`:507-511`) остаётся верным буквально, без оговорок.

**Минусы:** теряется «один список на оба хелпера» — аргумент, которым v3 обосновала передачу `calc_dates` второму хелперу. Но этот аргумент был про единственность **источника**, а не про единственность объекта: резерв «вчера», взятый как резерв «сегодня», — это одно и то же число из одного словаря, то есть FR-6 соблюдается даже строже (расхождение между «вчера» и «сегодня» по резерву становится физически невозможным, а не просто согласованным).

**Рекомендация:** рассмотреть наравне с вариантом «`yesterday = None` 1-го числа». Оба дешевле, чем ветвление внутри `_yesterday_slice`.
