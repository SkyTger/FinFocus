## 🔴 Критичные проблемы (Blockers)

### 1. `_payments_tail_by_day([yday], payments, payments_end)` вернёт ноль по построению — «вчера» получит `payments = 0` и завышенное `free`

**Где:**
- solution-v2, секция «Расширение модели слоёв», `_yesterday_slice`, строка `day_payments = self._payments_tail_by_day([yday], payments, payments_end)`
- Утверждение v2: «Обе вспомогательные функции уже принимают `window_dates: list[date]` — передача списка из одного дня их не меняет вообще»
- Факт: `money_layers_service.py:423-463`

**Проблема:**
Тело `_payments_tail_by_day` считает суффиксные суммы **проходом по переданному списку дат**, накапливая `tail` из этого же списка:

```python
result: dict[date, Decimal] = {}
tail = Decimal("0")
for day in reversed(window_dates):
    if day >= payments_end:
        result[day] = Decimal("0")
    else:
        result[day] = tail
    tail += by_day.get(day, Decimal("0"))
```

При `window_dates = [yday]`: цикл делает одну итерацию, `tail` ещё равен нулю, `yday < payments_end` почти всегда → `result[yday] = Decimal("0")`. Платежи дней `ref, ref+1, … payments_end` в `by_day` присутствуют (список `payments` собран целиком и фильтруется только `date <= payments_end`), но в хвост не попадают, потому что их дат нет в переданном списке. Функция не «точечная» — она **оконная**: смысл её результата определяется составом `window_dates`.

Дополнительно: `payments` собирается с фильтром `day >= reference_date` (`:404`), то есть платежей на самом `yday` в списке нет вовсе — но это как раз корректно (они уже вычтены из `balance(yday)`).

Второй аргумент, который тоже не сойдётся: в v2 вызов записан как `self._payments_tail_by_day([yday], payments, payments_end)`, а фактическая подпись — `(payments, window_dates, payments_end)` (`:423-428`). Аргументы переставлены. Это поймает первый же прогон, в отличие от главного дефекта.

По контрасту `_goals_part_by_day` при списке из одного дня **корректен**: он итерируется по `savings_by_date` целиком и внутри себя фильтрует по `[month_start(D), month_end(D)]` (`:580-595`), от состава `window_dates` не зависит. То есть «обе функции безопасны» — верно ровно наполовину, и v2 не различила эти два случая.

**Почему критично:**
Карточка «Календарь» покажет «Вчера» с завышенным слоем «Свободно» на всю сумму платежей остатка месяца — на наполненной базе это десятки тысяч рублей. Профиль дефекта тот же, от которого v2 защищалась в R3, только хуже:
- инвариант `free + payments + reserve == forecast_balance` **держится** (`_split_day` сохраняет сумму при любом входе, `:599-642`), поэтому заявленный тест инварианта для `yesterday` зелёный;
- целевой тест «`yesterday["forecast_balance"] != 0` на истории» тоже зелёный — баланс-то посчитан правильно;
- значение правдоподобно (не ноль, не отрицательное);
- ни один из шести тестов шага 1 не смотрит на `yesterday["payments"]`.

То есть весь набор страховок, выстроенный v2 вокруг «вчера», проходит мимо этого дефекта. И он бьёт прямо в FR-6: соседние окошки «вчера» и «сегодня» будут посчитаны по разной логике — та самая P1-боль аудита, ради лечения которой затевался кусок.

**Пример сценария:**
```
Сегодня 20-е, до конца месяца платежей на 40 000 ₽.
balance(19) = 100 000, balance(20) = 100 000.
«Сегодня»: payments = 40 000, reserve = 30 000, free = 30 000.
«Вчера»:   payments = 0,      reserve = 30 000, free = 70 000.
Пользователь видит: вчера свободно 70 000, сегодня 30 000,
                    при одинаковом остатке и без единой операции за день.
```

**Рекомендация:**
Не вызывать оконную функцию на одноэлементном списке. Два честных варианта, оба дешёвые:
1. **Считать хвост «вчера» из уже посчитанного окна.** Хвост на `yday` = хвост на `ref` + платежи дня `ref`: `payments_tail[yday] = payments_tail[ref] + Σ payments(date == ref)`. Одна строка, использует уже вычисленный `payments_tail` окна, ничего в существующих функциях не меняет. Требует явной проверки границы `ref > payments_end` (последний день месяца).
2. **Передать в `_payments_tail_by_day` расширенный список `[yday] + window_dates`** и взять из результата и `yday`, и дни окна. Функция вызывается один раз, семантика хвоста сохраняется по построению, `days` строится по-прежнему только из `window_dates`. Это, по-моему, чище: исчезает возможность разойтись между «вчера» и окном.

И обязательный тест, которого в v2 нет: **`yesterday["payments"] == today["payments"] + Σ платежей дня `ref`** на фикстуре с платежами внутри месяца, плюс mutation-проверка (обнулить слагаемое — тест должен покраснеть). Тест инварианта суммы этот класс дефектов не ловит принципиально, и это стоит написать в самом плане, чтобы следующая итерация не положилась на него снова.

### 2. Удаление `highlight_active_sidebar` оставляет `update_sidebar_profile` с условно присутствующими Output'ами — имя и аватар в сайдбаре ломаются

**Где:**
- solution-v2, секция «Сайдбар», комментарий: «`update_sidebar_profile` ОСТАЁТСЯ… значение подставляется при построении (`create_sidebar` уже читает профиль), а колбэк оставляется ТОЛЬКО ради `Input("profile-updated","data")` с guard'ом на dashboard-pathname»
- Факт: `sidebar.py:57-146` (`create_sidebar`), `:163-185` (`update_sidebar_profile`)

**Проблема:**
Утверждение «`create_sidebar` уже читает профиль» **неверно**. Проверил по коду: `create_sidebar()` не открывает сессию вообще и подставляет литералы — `"\U0001f60a"` в `sidebar-profile-avatar` (`:65`) и `"Пользователь"` в `sidebar-profile-name` (`:82`). Реальные имя и аватар приходят **только** из `update_sidebar_profile` (`:173-185`), который читает `OnboardingService.get_profile` и висит на двух Input'ах: `url.pathname` и `profile-updated`.

Отсюда три следствия, ни одно из которых v2 не разобрала:

1. **Если оставить колбэк как есть** (два Input'а, один из которых `url.pathname`) — получается ровно та гонка, из-за которой v2 удалила `highlight_active_sidebar`: `render_sidebar_slot` и `update_sidebar_profile` слушают один `Input("url","pathname")`, и второй пишет в узлы, которые первый в этот же момент создаёт или удаляет. Аргумент v2 против guard'а («гонка, а не шум») применим к `update_sidebar_profile` буквально — но там он не применён.
2. **Если убрать из него `url.pathname`** и оставить только `profile-updated` — при обычной навигации между разделами сайдбар пересоздаётся `render_sidebar_slot` и возвращается к литералам «Пользователь» + `😊`, а колбэк не сработает, потому что `profile-updated` не менялся. Пользователь будет видеть своё имя только сразу после сохранения профиля, а после любого перехода — снова «Пользователь». Это регрессия функциональности Epic-09 фазы 2 и, судя по формулировке, именно тот вариант, к которому подталкивает v2 («guard на dashboard-pathname»).
3. **Симметричный вопрос про Output'ы вообще не поставлен.** v2 в ответе на вопрос 2 сама пишет: правило C-6 задокументировано для Input'ов, про Output в KB правила нет, но `sidebar-nav` она всё же убрала из Output'ов «чтобы не было гонки». `sidebar-profile-name`/`-avatar` — точно такие же условно присутствующие Output'ы того же колбэка, оставленного жить. Решение противоречит собственному правилу через два абзаца.

**Почему критично:**
Это регрессия за пределами scope куска (профиль в сайдбаре — Epic-09 фаза 2), внесённая **правкой по критике v1**, то есть новая относительно v1. Она не ловится ни одним из заявленных тестов: `test_profile_modal_callbacks.py` адаптируется под вход через Store, а имя/аватар в сайдбаре тестами не покрыты вовсе. В ручном чек-листе шага 13 п. 4 проверяется «подсветка активного пункта», про имя и аватар — ни слова. Плюс класс дефекта совпадает с тем, который проект уже ловил дважды (протоколы 0026 и 0028/3.5-m-fix): «динамический элемент + колбэк, который про него не знает».

**Пример сценария:**
```
Пользователь Николай, аватар «кот».
Дашборд → клик «Календарь»
  → render_sidebar_slot создаёт сайдбар с литералами «Пользователь» + 😊
  → update_sidebar_profile (если Input pathname убран) не срабатывает
  → в сайдбаре «Пользователь» и смайлик вместо кота
  → клик по нему открывает модал с правильным именем (модал читает БД)
```

**Рекомендация:**
Довести решение до конца тем же приёмом, которым решён `sidebar-nav`: **читать профиль при построении**. `create_sidebar(pathname, profile)` (или `create_sidebar(pathname)` с чтением профиля внутри), `render_sidebar_slot` открывает одну сессию и передаёт профиль — тогда у сайдбара **ни одного** Output-колбэка не остаётся, и `update_sidebar_profile` удаляется целиком. Реакция на правку профиля обеспечивается тем, что `render_sidebar_slot` получает вторым Input'ом `profile-updated` (Store живёт в глобальном layout, присутствует всегда — C-6 соблюдён) и просто перерисовывает сайдбар. Один колбэк, один Output, ноль условно присутствующих узлов.

Цена — одна сессия на построение сайдбара при переходе между разделами; на дашборде её нет (возвращается `[]`), то есть бюджет NFR-1 не задет. Это надо явно отразить в «Стратегии загрузки»: сейчас там сессия сайдбара не учтена ни в одном варианте.

Плюс: добавить в ручной чек-лист шага 13 пункт «имя и аватар в сайдбаре корректны на всех четырёх разделах и после правки профиля», а в тесты — контракт входов `render_sidebar_slot` (`inspect.getsource`, как в `test_dashboard_callbacks.py`).

## 🟡 Важные проблемы (Should Fix)

### 3. Перечень границ объявлен «исчерпывающим», но `_is_empty` через `savings_by_date` от расширения `collect_start` всё же зависит

**Где:** solution-v2, таблица границ, строка `_is_empty` — «без изменений: `days` не изменился → семантика пустоты не переворачивается»; факт: `money_layers_service.py:751-810`, `:415-418`

**Проблема:**
Аргумент верен только для одного из четырёх условий `_is_empty`. Тело:

```python
if starting_balance != 0: return False
if has_recurring_templates: return False
if payments or savings_by_date: return False
return all(day["forecast_balance"] == 0 for day in days)
```

Третье условие смотрит на `savings_by_date`, а `savings_by_date` наполняется **всем** собранным диапазоном, начиная с `collect_start` (`:415-418`), без фильтра по датам. v2 расширяет `collect_start` до `min(_month_start(ref), ref - 1)` — то есть 1-го числа месяца диапазон захватывает последний день предыдущего месяца. Savings-операция на этом дне добавит ключ в `savings_by_date` и перевернёт `is_empty` с `True` на `False`.

Достижимость узкая (только 1-е число + пользователь с нулевым `starting_balance`, без recurring-шаблонов, с одной savings-операцией в конце прошлого месяца и нулевыми балансами окна), и направление безопасное (вместо пустого состояния — плоский график). Но утверждение «перечень исчерпывающий, `_is_empty` не затронут» в решении, которое строит на этой исчерпывающести весь свой риск-профиль (R5 «низкая»), — неверно. `payments` действительно не затронут: фильтр `day >= reference_date` (`:404`) отсекает вчерашний день гарантированно; про это v2 написала верно, а про `savings_by_date` — нет, хотя рядом сама же отмечает, что этот словарь «уже сегодня включает прошедшие дни месяца».

**Почему важно:**
Не из-за последствий (они мизерны), а из-за метода: «исчерпывающий перечень границ» — единственная гарантия, что реализация ничего не пропустит. Если в нём есть неверная строка, доверие к остальным падает, а следующая итерация может опереться на него так же, как эта опёрлась на «обе функции безопасны» (блокер №1).

**Рекомендация:**
Поправить строку таблицы: назвать зависимость через `savings_by_date`, оценить последствие (`is_empty` может стать `False` 1-го числа) и решить явно — принять (с одной строкой в докстринге `_is_empty`) либо отфильтровать `savings_by_date` по `>= _month_start(ref)` при передаче в `_is_empty`. Первое дешевле и, по-моему, достаточно. В набор тестов шага 1 добавить фикстуру «1-е число + savings-операция 31-го прошлого месяца» — она уже почти есть (п. 6), нужен только ассерт на `is_empty`.

### 4. `OperationRow.date: date` против `RecentTransaction["date"]: str` — контракт карточки не сходится с источником

**Где:** solution-v2, `app/schema/panel.py::OperationRow`; факт: `dashboard_service.py:456-472` (`_map_transactions` пишет `date=t.transaction_date.isoformat()`), схема `RecentTransaction`

**Проблема:**
`OperationRow` объявляет `date: date`, а единственный источник строк — `DashboardService.get_recent_transactions` / `get_upcoming_transactions` — отдаёт ISO-**строку**. Значит `_operations_block` обязан делать `date.fromisoformat(...)` обратно, и об этом в решении не сказано ни в интерфейсе, ни в шаге 3. Мелочь, но она попадает в `format_date_human` (подпись «5 февраля»), то есть пойдёт в UI: при передаче строки форматтер либо упадёт, либо выведет мусор, и это уйдёт под `try/except` блока → карточка деградирует в `FAILED` целиком на нормальных данных.

Похожий недосказ в `OperationRow.kind: Literal["income","expense","other"]`: источник даёт `transaction_type` строкой значения enum (пять возможных значений, включая `adjustment`, `transfer`, `savings_*`), правило сведения пяти значений к трём в решении не задано. Для карточки, где знак суммы определяет цвет, это не косметика.

**Почему важно:**
Оба места — контракт между блоком и build-функцией, а тесты карточек кормятся словарями по этому же контракту. Значит расхождение источника и контракта тестами не ловится по построению: тест положит в фикстуру `date(2026,8,25)`, а прод получит `"2026-08-25"`.

**Рекомендация:**
В шаге 3 явно записать преобразование (`date.fromisoformat`) и таблицу сведения `transaction_type` → `kind` (какие пять значений в какие три). Добавить один тест сервиса, проверяющий тип `panel["operations"]["recent"][0]["date"]` — `isinstance(..., date)`. Это тот же приём, что уже применён для материализации ORM.

### 5. Карточка «Аналитика»: `month_total` от `get_expenses_by_category` не сопоставим с расходами графика — FR-6 требует это назвать

**Где:** solution-v2, шаг 3 `_analytics_block`, RTM #12/#31; факт: `analytics_service.py:94-100`

**Проблема:**
`get_expenses_by_category` фильтрует `Transaction.transaction_type == EXPENSE` **и** `Transaction.is_recurring == False`. То есть:
- виртуальные инстансы регулярных платежей в цифру не входят (в отличие от слоя «Платежи» графика, который их считает через `CalendarService`);
- `savings_reserve` / `savings_contribution` / отрицательные `adjustment` тоже не входят, а в слой «Платежи» входят (`money_layers_service.py:397-402`).

Карточка сойдётся с разделом «Аналитика» (тот же сервис — это правильно), но **не** сойдётся с графиком щитка, стоящим прямо над ней. RTM #31 при этом утверждает «цифры карточек не противоречат шапке/графику» и относит к этому же пункту аналитику через формулировку «один `get_money_layers` за сборку».

**Почему важно:**
FR-6 и P1-боль аудита — про «цифры соседних элементов противоречат друг другу на глаз». Пользователь увидит «расходы августа 78 400 ₽» под графиком, где месячный слой платежей заметно больше. Это не дефект (обе цифры корректны в своей семантике), но именно необъявленное расхождение и было болезнью, которую кусок лечит. Ограничение по регулярным операциям v2 честно назвала для карточки «Операции» — здесь ровно тот же случай, и он пропущен.

**Рекомендация:**
Назвать семантику явно: в докстринге `AnalyticsCardData` и в подписи карточки — что именно считается («расходы» = операции типа EXPENSE, без регулярных и без взносов в цели), симметрично тому, как оформлено ограничение карточки «Операции». Добавить строку в RTM. Если владелец захочет сопоставимости — это уже правка `AnalyticsService`, то есть C-3, и решать надо отдельно; сейчас достаточно объявить.

### 6. `_goals_block` на чистой базе даст `FAILED`, а не `EMPTY` — AC-5 под вопросом

**Где:** solution-v2, шаг 3 `_goals_block`, обработка ошибок; факт: `goal_service.py:458-476` и `:512-529` — `get_savings_budget` и `get_savings_mode` бросают `ValidationError`, если пользователь не найден

**Проблема:**
Оба вызова, на которые опирается `_goals_block`, бросают исключение при отсутствующем пользователе. На чистой базе бутстрап создаёт `User(id=1)` (Epic-09 фаза 1), поэтому в проде это скорее не выстрелит. Но:
- AC-5 проверяется тестом «пустая база → все блоки `EMPTY`», и если фикстура пустой базы не создаёт пользователя (а это самый естественный способ написать «пустая база»), тест получит `goals = FAILED` и либо покраснеет, либо — хуже — будет подкручен под `FAILED`, и AC-5 окажется формально зелёным при нарушенном требовании;
- поведение «нет пользователя → карточка Цели сообщает о сбое» само по себе неверное: это не сбой, это пустота. `MoneyLayersService` для того же случая специально сделан не бросающим (`_user_data_markers`: «на отсутствующем пользователе — `(0, False)`: чистая база штатна»).

**Почему важно:**
AC-5 — один из десяти критериев приёмки, и это единственное место, где заявленный тест может дать ложнозелёный результат по причине, лежащей вне карточек.

**Рекомендация:**
В `_goals_block` обработать отсутствие пользователя как `EMPTY`, а не как сбой: либо ловить `ValidationError` отдельной ветвью перед общим `except`, либо читать `monthly_savings_budget`/`savings_mode` тем же `session.get(User, uid)`, что уже нужен для `cushion_target` (и заодно уйдёт два вызова из стратегии загрузки). Явно записать в шаге 4, что фикстура «пустая база» — **с** пользователем и **без** пользователя, и в обоих случаях ожидается `EMPTY`.

### 7. `calendar-focus-date` — Store как состояние: приёмник переприменит фокус при возврате на календарь

**Где:** solution-v2, шаг 9, `calendar.py`: «`Input("calendar-focus-date")` в существующий `load_and_navigate_calendar`»; R10; факт: `calendar.py:758-799`

**Проблема:**
v2 знает про «Store — состояние, а не событие» и ставит guard в `open_wishlist_modal` и в `handle_profile_modal`. Для `calendar-focus-date` тот же guard не описан, хотя ситуация опаснее: `load_and_navigate_calendar` — не модал, а основной колбэк календаря с Input'ами навигации (`prev/next/today`) и `wishlist-active-item`. Store хранит значение до перезагрузки страницы, layout между переходами не пересоздаётся. Значит:

```
Дашборд → клик «завтра» → /calendar?focus_date=2026-08-26 (фокус применён)
Пользователь листает на октябрь
Уходит в «Операции», возвращается в «Календарь» кликом меню
  → pathname меняется → load_and_navigate_calendar срабатывает
  → calendar-focus-date всё ещё содержит 2026-08-26
  → календарь молча прыгает на август
```

Тот же эффект даёт любое срабатывание колбэка по другому Input'у, если реализация читает `focus_date` не через `ctx.triggered_id`. И ровно эту болезнь v2 сама описала для профиля: «Store сохраняет значение между переходами, из-за чего окно профиля стало всплывать при каждой загрузке страницы».

**Почему важно:**
Тихая регрессия навигации календаря, задевающая существующее поведение (C-1 «разделы содержательно не пересматриваются»). В ручном чек-листе шага 13 проверяется переход дашборд → календарь, но не «ушёл и вернулся».

**Рекомендация:**
Описать в шаге 9 механику одинаково для обоих новых Store'ов: значение timestamp-обёрнуто (это уже сказано), приёмник реагирует **только** когда `ctx.triggered_id` — это сам Store, и сравнивает применённый timestamp с сохранённым в `calendar-state` (там уже есть словарь состояния, ключ `focus_date` v2 и так добавляет — храните рядом `focus_applied_ts`). Тот же абзац — для `goals-focus-goal`. Добавить в шаг 13 пункт «уход из раздела и возврат по меню не переприменяет фокус».

## 🟢 Незначительные замечания (Optional)

### 8. «Сессий за рендер: 1 (было 4)» — фактически было 3

Проверил: `dashboard.py` открывает сессию в `_load_dashboard_components` (`:1002`) и в `_build_cushion_card_readonly` (`:871`); третья — в `build_wishlist_widget` (`wishlist.py:33`), который вызывается **из layout** (`dashboard.py:687`), а не из колбэка. Четвёртой нет: профиль читается внутри той же сессии, что и слои (`:1003-1004`). Заодно это значит, что виджет wishlist сегодня не обновляется по `global-transaction-trigger` — карточка это попутно исправит, что стоит упомянуть как побочный выигрыш. Цифру в докстринге поправить, иначе она поедет в knowledge-bank как факт.

### 9. `WINDOW_LOOKBACK_DAYS` и `WINDOW_LOOKBACK_DAYS_TD` — две константы на одно понятие

В тексте используются обе (`ref - WINDOW_LOOKBACK_DAYS` в таблице границ и `ref - WINDOW_LOOKBACK_DAYS_TD` в `_yesterday_slice`). Нужна одна; если это `int` дней, то арифметика с `date` требует `timedelta` в каждом месте — либо оставить только `timedelta`-вариант, либо только `int` и `timedelta(days=…)` на месте. Мелочь, но константа объявляется в схеме с большим докстрингом, то есть станет частью публичного контракта.

### 10. `dip_href` при пустом окне

`min_free_date` в `_window_min_free` при пустом `days` возвращает `date.today()` (`:690-691`), а не `None`. `CalendarCardData.dip_date` объявлен `date | None`, и при `status=EMPTY` карточка не должна рисовать маркер вовсе. Стоит одной строкой сказать, что источник `dip_*` игнорируется при `EMPTY` — иначе на чистой базе появится «Ближайшая просадка: сегодня, 0 ₽», то есть числовой артефакт, запрещённый AC-5. Тест «пустые состояния без `₽`/`%`» это поймает, но лучше зафиксировать намерение.

## 🔄 Альтернативные подходы

### Подход A: один вызов `_payments_tail_by_day` на расширенном списке дат

**Идея:**
Вместо второго точечного вызова передать `[yday] + window_dates` в существующий `_payments_tail_by_day` и в `_goals_part_by_day`, а `days` собирать по-прежнему только из `window_dates`, `yesterday` — из того же результата по ключу `yday`.

**Плюсы:**
- Семантика хвоста платежей для «вчера» верна по построению, а не по отдельной формуле — расхождение между «вчера» и «сегодня» становится невозможным (это и есть FR-6 в миниатюре).
- Ни одна из двух вспомогательных функций не вызывается в режиме, для которого не написана; C-3 для приватных хелперов соблюдён по-настоящему.
- Число вызовов не растёт: было два (`payments_tail`, `goals_part`) — остаётся два.
- Форма `days` не меняется, то есть все выигрыши «аккуратного варианта» (нулевой blast radius куска 1, 47 тестов без правок) сохраняются полностью. Это не откат к отброшенному владельцем сдвигу окна — окно модели остаётся тем же, меняется только служебный список дат, по которому считаются хелперы.

**Минусы:**
- Списки дат для хелперов и для `days` перестают совпадать — нужен внятный локальный именованный список (`calc_dates` против `window_dates`) и одна строка докстринга, иначе следующий читатель решит, что окно всё-таки сдвинуто.

**Почему может быть лучше:**
Вариант из блокера №1 п.1 («хвост `yday` = хвост `ref` + платежи дня `ref`») тоже верен и ещё дешевле, но вводит вторую формулу для того же понятия — а именно от вторых формул для одного понятия лечит весь кусок.

**Рекомендация:**
Выбрать один из двух в v3 и явно сказать, почему; в обоих случаях добавить тест на `yesterday["payments"]` и mutation-проверку.

### Подход B: сайдбар полностью статичен по данным, кроме pathname и профиля

**Идея:**
`render_sidebar_slot(pathname, profile_updated)` — один колбэк, два Input'а (оба на элементы, присутствующие всегда: `url` и Store), внутри одно чтение профиля, `create_sidebar(pathname, profile)` — чистая функция. Колбэки `highlight_active_sidebar` и `update_sidebar_profile` удаляются оба.

**Плюсы:**
- У сайдбара не остаётся ни одного Output на условно присутствующий элемент — правило, которое v2 сама вывела, применяется до конца.
- Минус два колбэка вместо минус одного; класс регрессий, дважды ловленный проектом, закрывается конструктивно.
- Реакция на правку профиля сохраняется без guard'ов на pathname.

**Минусы:**
- Одна сессия на построение сайдбара при переходе между разделами (на дашборде — ноль). Надо внести в стратегию загрузки.

**Почему может быть лучше:**
Это ровно тот же приём, которым v2 решила `sidebar-nav`, доведённый до второго условно присутствующего Output'а того же компонента. Половинчатое применение собственного правила — то, что критика обязана поймать.
