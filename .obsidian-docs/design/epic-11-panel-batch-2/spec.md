> Раскрой эпика: 3 куска (решение владельца 2026-08-24, габарит-гейт

## Цель

Дашборд становится навигацией: карточки — живые фрагменты разделов и
единственная точка входа в них (метафора электрощитка — прорези на
лицевой панели), меню с дашборда убирается. Клик по карточке —
«открытие панели»: переход в раздел с сохранением контекста клика.
Это уровень 3 иерархии внимания design.md (после шапки-вердикта и
графика, реализованных куском 1).

## Контекст

- **Источник правды по концепции**: `.obsidian-docs/discussions/_archive/dashboard-as-menu-2026-08-23/design.md`
  (20 решений, принято владельцем 2026-08-23). Ядро: карточки как
  живые фрагменты + переход с сохранением контекста; «дух важнее
  буквы» — позиционная привязка «фрагмент ровно там же, где в полном
  разделе» НЕ требование.
- **Эскиз принят**: `.visual/finfocus-panel-dashboard/v3.html` —
  основа визуальной реализации, включая раскладку карточек.
  Не-блокирующая заметка vision-критика для этого куска — в осадке.
- **Состояние после куска 1** (KB: `modules/ui-components.md` →
  Dashboard-щиток, `modules/services.md` → MoneyLayersService):
  дашборд = шапка «Свободно сегодня» + график полос (единый источник —
  `MoneyLayersService`), ниже — split-таблицы «Недавние/Предстоящие
  операции» и правая колонка Wishlist-виджет + readonly-карточка
  подушки (наследие протокола 0023). Сайдбар — на всех страницах,
  включая дашборд. Онбординг-тост нулевого баланса живёт на дашборде.
- **Механики-сироты** (инвентаризация ревью 2026-08-23): вход в
  «Сверку» — закрыт куском 1 (кнопка в шапке); «Доходы за месяц» —
  убран куском 1 осознанно (решение FR-5.b, сужено владельцем
  2026-08-25: показатель не возвращается и в куске 2); остаётся
  онбординг-тост нулевого баланса.
- **Данные для карточек уже есть в сервисном слое** (KB:
  `modules/services.md`): балансы дней и модель слоёв
  (CalendarService/MoneyLayersService), цели и приоритеты
  (GoalService), порог и статус подушки (CushionService), недавние и
  предстоящие операции (DashboardService), структура расходов месяца
  (AnalyticsService), фокусные хотелки (WishlistService.get_focus).
- **Инфраструктура переходов**: единый callback query params в
  `app/main.py` (`?open_recon=1`, `?wishlist_item=ID` через
  Store-триггеры), фильтр периода `/transactions?start=&end=`
  (протокол 0023). Фокуса цели на `/goals` и открытия календаря на

- **Мотивация**: UX-аудит 2026-08-20 — P1-боль «цифры соседних
  карточек противоречат друг другу» лечится питанием карточек от
  единой модели; конституция щитка защищает находимость разделов
  после снятия меню.

## Функциональные требования

- **FR-1. Карточки-двери по принятой проекции разделов** (design.md +
  решения владельца 2026-08-25):
  - *Календарь*: вчера / сегодня / завтра (остатки дней) + маркер
    просадки — день минимума слоя «Свободно» окна модели; при
    минимуме ≤ 0 маркер визуально усиливается (факт знака числа, не
    порог-вердикт — в духе решения куска 1). Дверь: календарь на
    кликнутом дне.
  - *Цели*: топ-цель с прогрессом + сводка остальных (вида «по плану /
    1 отстаёт») + статус подушки одной строкой — подушка живёт внутри
    этой карточки и отдельной не имеет. Дверь: цели с фокусом на
    кликнутой.
  - *Операции*: 2-3 недавние + 2-3 предстоящие. Дверь: список операций
    с фильтром периода.
  - *Аналитика*: цифра месяца — топ-категория расходов + мини-структура.
    Показатель «Доходы за месяц» НЕ возвращается (решение владельца
    2026-08-25). Дверь: аналитика текущего месяца.
  - *Wishlist*: компактный виджет (не пункт меню — представительство
    сохраняется). Дверь двухуровневая: заголовок/тело карточки →
    модал управления wishlist; клик по конкретной хотелке → календарь
    в режиме покупок с фокусом на ней.
  - *Настройки*: служебная иконка (шестерёнка шапки, есть с куска 1),
    не карточка.
- **FR-2. Конституция щитка.** Каждый предметный пункт меню имеет
  карточку; на дашборде меню нет — сайдбар с дашборда убирается,
  карточки и есть навигация. На остальных страницах сайдбар остаётся
  (промежуточное состояние принято; полоска-меню — кусок 3).
- **FR-3. Переход с сохранением контекста.** Клик по элементу карточки
  открывает раздел в состоянии, соответствующем клику: «завтра» →
  календарь с завтрашним днём; цель → фокус на ней; операции → фильтр
  периода; аналитика → текущий месяц. «Дух важнее буквы»: контекст —
  требование, позиционная привязка фрагмента — нет.
- **FR-4. Механики-сироты.** Онбординг-тост нулевого баланса
  сохраняет своё поведение на перестроенном дашборде (не теряется
  молча). Прочие сироты инвентаризации закрыты ранее (см. Контекст).
- **FR-5. Пустые состояния.** У нового пользователя (0 операций,
  0 целей, пустой wishlist) каждая карточка показывает
  спроектированное пустое состояние: без числовых артефактов, с
  понятным смыслом раздела; карточки не исчезают (конституция FR-2) —
  это первое впечатление бета-тестера.
- **FR-6. Единая модель и стратегия загрузки.** Карточки питаются
  данными, согласованными с шапкой и графиком: там, где применимо
  (карточка «Календарь»), — той же моделью слоёв куска 1; цифры
  карточек не противоречат шапке/графику. Открытие дашборда тянет
  фрагменты всех разделов — стратегия загрузки (сколько вызовов,
  кеширование/ленивая подгрузка) проектируется явно с бюджетом NFR-1,
  а не складывается стихийно.

## Нефункциональные требования

- **NFR-1. Производительность.** Открытие дашборда со всеми карточками
  на наполненной локальной базе — не медленнее ориентира куска 1:
  < 2 секунд (метрика ROADMAP «время загрузки < 2 сек»).
- **NFR-2. Наблюдаемость и деградация.** Сбой сборки данных одной
  карточки не обрушивает дашборд целиком: карточка деградирует с
  индикацией, сбой логируется с трейсбеком
  (`logger.opt(exception=True)` — идиома проекта, протокол 0027).
  Сбой расчёта базовой модели остатка не глотается (правило куска 1).

## Ограничения

- **C-1.** Разделы (календарь, цели, операции, аналитика) содержательно
  не пересматриваются. Допустимы только минимальные приёмники
  контекста переходов FR-3 (например, обработка новых query params) —
  без изменения логики разделов.
- **C-2.** Дисциплина сервисного слоя сохраняется: Decimal для денег,
  session-контракт flush()/commit(), сервисы не знают о Dash
  (KB: `architecture.md`).
- **C-3.** Существующее поведение сервисов не меняется — данные
  карточек собираются композицией/расширением; полный прогон тестов
  (693 на 2026-08-25) остаётся зелёным.
- **C-4.** Схема БД не меняется. Если проектирование покажет
  необходимость — фиксировать отдельным решением, не молча.
- **C-5.** Контракт `MoneyLayersService`/`MoneyLayersData` МОЖНО
  менять (его стабильность до куска 2 не гарантировалась — осознанное
  решение спеки куска 1), но шапка и график продолжают работать, а
  инвариант «сумма слоёв == остаток кассового календаря» сохраняется.
- **C-6.** Новые интерактивные элементы дашборда не ломают колбэки на
  других страницах: прямой Input на элемент, существующий только на
  дашборде, молча отключает колбэк целиком на остальных страницах —
  известный класс регрессий проекта (протоколы 0026, 0028/3.5-m-fix;
  паттерн — KB `patterns/callbacks.md`, Store-триггер).
- **C-7.** Шапка и график куска 1 визуально и поведенчески не
  регрессируют: решения владельца (нет вердикта-светофора, нет
  приветствия, шапка не дверь) остаются в силе; 47 тестов визуального
  слоя щитка (протокол 0029) остаются зелёными или осознанно
  адаптируются под новую раскладку.

## Критерии приёмки

- **AC-1.** Дано: наполненная база. Когда: открыт `/dashboard`. Тогда:
  под шапкой и графиком видны карточки пяти предметных разделов
  (Календарь, Цели, Операции, Аналитика, Wishlist); сайдбара/меню на
  дашборде нет; на `/calendar`, `/goals`, `/transactions`, `/analytics`
  сайдбар присутствует как раньше.
- **AC-2.** Переходы с контекстом: клик по «завтра» в карточке
  Календарь открывает календарь с завтрашним днём; клик по цели —
  `/goals` с фокусом на этой цели; клик по операциям — `/transactions`
  с фильтром периода; клик по карточке Аналитика — `/analytics` с
  данными текущего месяца.
- **AC-3.** Согласованность цифр: остаток «сегодня» в карточке
  Календарь равен значению модели слоёв на сегодня (тому же, из
  которого построена шапка) — проверено unit-тестом.
- **AC-4.** Карточка Цели содержит топ-цель с прогрессом, сводку
  остальных целей и строку статуса подушки; отдельной карточки подушки
  на дашборде нет (readonly-карточка подушки старой раскладки снята);
  split-таблицы операций старой раскладки заменены карточкой Операции.
- **AC-5.** Дано: чистая база (онбординг пропущен). Когда: открыт
  дашборд. Тогда: все пять карточек на месте (конституция) и
  показывают спроектированные пустые состояния без числовых
  артефактов.
- **AC-6.** Онбординг-тост нулевого баланса появляется и ведёт себя на
  новом дашборде так же, как до перестройки.
- **AC-7.** Маркер просадки: на фикстуре с минимумом «Свободно» > 0
  карточка Календарь показывает день минимума без усиления; на
  фикстуре с минимумом ≤ 0 — маркер визуально усилен — проверено
  unit-тестами.
- **AC-8.** Дверь Wishlist: клик по заголовку/телу карточки открывает
  модал управления wishlist; клик по конкретной хотелке открывает
  календарь в режиме покупок с фокусом на ней.
- **AC-9.** Модал профиля открывается со всех страниц обоими входами
  (аватар сайдбара на не-дашборд страницах, шестерёнка шапки на
  дашборде) — регрессия класса C-6 отсутствует.
- **AC-10.** Новые данные и UI покрыты unit-тестами; полный прогон
  pytest зелёный; black + flake8 без новых замечаний; рендер дашборда
  на наполненной базе укладывается в NFR-1 (замер как в куске 1).

## Стек-специфичные секции

**Миграции БД**: не применимо — изменение схемы не заявлено (C-4).

**Контракты API**: не применимо — внешних API нет; внутренние
контракты — TypedDict-схемы (`app/schema/`), данные карточек
оформляются в том же стиле; допустимая эволюция `MoneyLayersData` —
по C-5.
