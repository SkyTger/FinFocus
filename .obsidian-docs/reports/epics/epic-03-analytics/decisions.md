# Epic-03: Решения (Decisions)

## D012: Тип ADJUSTMENT вместо флага is_adjustment

**Дата**: 2026-01-22
**Статус**: Утверждено

### Контекст
Для механизма сверки нужен способ создавать корректирующие операции. Два варианта:
1. Флаг `is_adjustment=True` на INCOME/EXPENSE
2. Отдельный тип `TransactionType.ADJUSTMENT`

### Решение
**Отдельный тип ADJUSTMENT**

### Обоснование
1. **Семантическая чистота** — корректировка не "доход" и не "расход", это синхронизация модели с реальностью
2. **Аналитика проще** — `WHERE type = 'income'` без дополнительных фильтров
3. **Расширяемость** — можно добавить метаданные (reconciliation_date, expected_balance)
4. **Account модель в будущем** — reconciliation логически отдельная сущность

### Реализация
```python
class TransactionType(Enum):
    INCOME = "income"       # +amount к балансу
    EXPENSE = "expense"     # -amount от баланса
    TRANSFER = "transfer"   # 0 (между счетами)
    ADJUSTMENT = "adjustment"  # ±amount (знак в самом amount)
```

В CalendarService: `if type == ADJUSTMENT: balance += amount` (со знаком)

## D013: Category как отдельная модель

**Дата**: 2026-01-22
**Статус**: Утверждено

### Контекст
Как хранить категории — enum в коде или отдельная таблица?

### Решение
**Отдельная модель Category** (справочник)

### Обоснование
1. Пользователь сможет добавлять свои категории (будущее)
2. Можно хранить метаданные (иконка, цвет, тип)
3. Легче делать аналитику (JOIN vs string matching)

### Структура
```python
class Category(Base):
    id: int
    name: str           # "Еда", "Транспорт"
    icon: str           # "bi-cart", "bi-car-front"
    type: str           # "income" / "expense" / "both"
    is_system: bool     # True = предзаполненная, нельзя удалить
    sort_order: int     # Порядок отображения
```

### Предзаполненные категории (15 базовых)
**Расходы**: Еда, Транспорт, Жилье, Связь, Здоровье, Одежда, Развлечения, Образование, Подарки, Прочее
**Доходы**: Зарплата, Подработка, Инвестиции, Подарки, Прочее

## D014: "Без категории" как валидное состояние

**Дата**: 2026-01-22
**Статус**: Утверждено

### Контекст
Должна ли категория быть обязательной при создании операции?

### Решение
**Нет. Category_id nullable, "Без категории" — норма.**

### Обоснование
1. Снижает барьер входа — пользователь не обязан думать о категории при каждом вводе
2. Аналитика работает с частичными данными — сегмент "Без категории" показывает покрытие
3. Соответствует философии: кассовый календарь требует сумм, категории — опциональны

### Реализация
- `Transaction.category_id` — nullable FK
- В аналитике: отдельный сегмент "Без категории"
- Подсказка "N операций без категории" для мотивации доразметить

## D015: Recurring наследует категорию из шаблона

**Дата**: 2026-01-22
**Статус**: Утверждено

### Контекст
Как работает категоризация для повторяющихся операций?

### Решение
**Шаблон (recurring template) хранит category_id, все генерируемые инстансы наследуют его.**

### Обоснование
1. Соответствует ожиданиям — зарплата всегда "Зарплата", аренда всегда "Жилье"
2. Один раз настроил — забыл
3. При изменении категории шаблона — новые инстансы получают новую категорию

### Реализация
- `Transaction.category_id` уже есть
- RecurringService при генерации копирует category_id из шаблона
- Инстанс можно перекатегоризировать индивидуально (exception)

## D016: Сверка — мини-диалог с ясной семантикой

**Дата**: 2026-01-22
**Статус**: Утверждено

### Контекст
Как пользователь выполняет сверку?

### Решение
**Модал на календаре с тремя элементами:**
1. Показать расчетный баланс на сегодня
2. Инпут для фактического остатка
3. Показать разницу и кнопка "Создать корректировку"

### UX Flow
1. Пользователь видит на календаре "Остаток: 15 000₽"
2. Проверяет реальный счет: 14 200₽
3. Нажимает "Сверка"
4. Вводит 14 200
5. Система показывает: "Разница: -800₽"
6. Кнопка "Создать корректировку" → ADJUSTMENT на -800₽
7. Календарь обновляется, остаток = 14 200₽

### Категория корректировки
По умолчанию: "Коррекция" (системная категория)
Можно изменить на стандартную (если вспомнил что забыл записать)
