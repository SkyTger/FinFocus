## 3. Цепочка потери требований

### Исходная спецификация (postponed-purchases-spec.md, секция 5.3):
```
- Рекомендованные дни: подсвечены (салатный фон).
- Нерекомендованные дни: серый фон + маркеры.
- Оранжевый маркер: порог подушки нарушен.
- Красное число (минус): касса < 0.
```

### Solution-v3.md (архитектурное решение):
```
# Не содержит детального описания CSS стилей
# Фокус на архитектуре: сервисы, модули, JS hover
```

### Protocol Step 07 (07-calendar-wishlist.md):
```
- Легенда маркеров: зелёный (безопасно), красный (риск)
- Маркер safe/unsafe (цвет рамки или точки)
```
**Потеря #1**: Нет упоминания "салатный фон" → заменено на "рамка"
**Потеря #2**: Нет оранжевого цвета → упрощено до зелёный/красный
**Потеря #3**: Нет серого фона для unsafe → не упоминается

### Protocol Step 08 (08-calendar-extension.md):
```
- .calendar-day.wishlist-safe — зелёная рамка/индикатор
- .calendar-day.wishlist-unsafe — красная рамка/индикатор
```
**Закрепление ошибки**: "рамка" явно указана, фон не упоминается

### Реализация (wishlist.css):
```css
.wishlist-day-safe { border-left: 3px solid #198754 !important; }
.wishlist-day-unsafe { border-left: 3px solid #dc3545 !important; }
```
**Результат**: Только border, без background

## 4. Причины расхождений

### 4.1 Архитектурный фокус critique
Critique-v1, v2, v3 проверяли:
- Соответствие Dash API (MutationObserver vs clientside_callback)
- SOLID принципы и модульность
- Производительность JS hover
- Обработку edge cases

Critique **НЕ проверял**:
- Соответствие визуальных стилей секции 5.3 спецификации
- Полноту цветовой палитры маркеров

### 4.2 Упрощение при написании protocol steps
- Шаг 07 был написан с фокусом на архитектуру модуля
- Визуальные детали из спецификации не были перенесены дословно
- "цвет рамки или точки" — двусмысленность привела к выбору border

### 4.3 Отсутствие UI review
- Не было отдельного этапа визуальной проверки
- Screenshot comparison со спецификацией не выполнялся

## 5. Технический анализ Safe/Unsafe логики

### PurchaseRecommendationService возвращает причины:
```python
SafeDateInfo = TypedDict('SafeDateInfo', {
    'safe': bool,
    'reasons': list[str],  # ["cushion_violated", "negative_balance"]
})
```

**Данные есть**, но CSS не различает причины:
- Все unsafe дни получают одинаковый класс `.wishlist-day-unsafe`
- Reasons доступны в tooltip, но не в визуальных маркерах

## 6. Рекомендации по исправлению

### Вариант A: Минимальные изменения (рекомендуется для MVP)
1. Заменить border-left на background-color:
   ```css
   .wishlist-day-safe { background-color: rgba(25, 135, 84, 0.1); }
   .wishlist-day-unsafe { background-color: rgba(108, 117, 125, 0.1); }
   ```
2. Добавить CSS для маркеров cushion vs negative:
   ```css
   .wishlist-marker-cushion { color: #fd7e14; } /* orange */
   .wishlist-marker-negative { color: #dc3545; } /* red */
   ```
3. Обновить calendar_wishlist.py для генерации маркеров по reasons

### Вариант B: Полная реализация по спецификации
1. Все изменения из Варианта A
2. Точечные маркеры (dots) вместо текстовых индикаторов
3. Легенда в overlay с визуальными примерами маркеров
4. Hover tooltip с объяснением каждой причины

### Effort оценка:
- Вариант A: ~2-3 часа (CSS + minor Python changes)
- Вариант B: ~4-6 часов (CSS + Python + UI adjustments)

## 8. Выводы

1. **Функциональность реализована корректно** — wishlist workflow работает: CRUD, calendar mode, hover, preselection, orphan detection.

2. **Визуальное представление расходится со спецификацией** — border вместо background, отсутствует оранжевый маркер для подушки.

3. **Причина — потеря деталей на этапе spec → solution → protocol steps** — архитектурный critique не включал UI validation.

4. **Исправление возможно без архитектурных изменений** — данные о причинах unsafe уже доступны в сервисе.
