# DELEGATION_GUIDE.md - Руководство по работе с субагентами

Детальное руководство для главного агента по делегированию задач и обновлению документации.

**Последнее обновление**: 2025-10-24

---

## 🎯 Цель

Эффективное делегирование задач субагентам с минимальной перегрузкой контекстом и автоматической синхронизацией документации.

---

## 🏗️ Архитектура системы делегирования

### Принцип гибридной памяти

**Два уровня памяти:**

1. **Глобальный контекст** (главный агент):
   - `CLAUDE.md` - контракт проекта
   - `ROADMAP.md` - план и прогресс
   - `feature_progress.md` - история последних 5 батчей

2. **Локальные протоколы** (субагенты):
   - `.protocol.md` - временная задача (10-30 строк)
   - Удаляется после выполнения

**Ключевой принцип**: Субагент видит ТОЛЬКО `.protocol.md`, не имеет доступа к глобальной документации.

---

## 🔄 Workflow делегирования

```
Задача возникает
  ↓
Главный агент создает .protocol.md
  ↓
Технический субагент (@code-search, @python-refactor, @qa-engineer) выполняет
  ↓
Главный агент анализирует результаты
  ↓
Главный агент обновляет глобальную документацию
  ↓
Удаляет .protocol.md
```

**Важно**: Главный агент самостоятельно обновляет документацию, НЕ делегирует это @doc-manager.

---

## 📝 Формат .protocol.md

### Локация и правила

- **Файл**: `/project-root/.protocol.md` (корень проекта)
- **Правило**: Один файл на одну активную задачу (без нумерации)
- **Жизненный цикл**: Создан → Выполнен → Удалён

### Структура файла

```markdown
# Задача: [Конкретная задача в одном предложении]

## Контекст
[2-3 предложения минимум для понимания]

## Критичные детали
- **Терминология**: [Если есть специфичные термины]
- **Формулы**: [Если есть бизнес-логика расчетов]
- **Ограничения**: [Если есть технические или бизнес-ограничения]

## Файлы
- `path/to/file.py:45-67` - краткое описание назначения
- `path/to/other.py` - краткое описание назначения
```

### Примеры хороших .protocol.md

**Пример 1: Поиск в кодовой базе**
```markdown
# Задача: Найти все функции расчета маржинальности

## Контекст
Нужно убедиться что формула margin_pct = (custom_profit / revenue) × 100%
используется везде корректно после исправления D014.

## Критичные детали
- **Терминология**: margin_pct (маржинальность %), custom_profit (маржа ₽)
- **Формула**: margin_pct = (custom_profit / revenue) × 100% (БЕЗ cashback/commission)

## Файлы
- `app/utils/metrics.py` - SOURCE OF TRUTH для всех формул
- `app/data/clickhouse_loader.py` - SQL запросы с расчетами
- `app/components/*.py` - Визуализации использующие margin_pct
```

**Пример 2: Рефакторинг**
```markdown
# Задача: Упростить функцию load_kpi_metrics() - удалить дублирование

## Контекст
Функция содержит повторяющиеся блоки расчета MoM%.
Вынести в helper функцию для переиспользования.

## Критичные детали
- **Ограничения**: НЕ менять формулы расчета, только структуру кода
- **Тесты**: Убедиться что результаты идентичны после рефакторинга

## Файлы
- `app/data/clickhouse_loader.py:268-340` - функция load_kpi_metrics()
```

**Пример 3: Тестирование**
```markdown
# Задача: Валидация формул margin_pct и roi_pct для всех вебмастеров

## Контекст
После исправления D014 нужно проверить корректность расчетов на всех данных.

## Критичные детали
- **Формулы**:
  - margin_pct = (custom_profit / revenue) × 100%
  - roi_pct = (final_profit / payout) × 100%
- **Ожидания**: margin_pct > roi_pct (т.к. final_profit учитывает больше расходов)

## Файлы
- `scripts/validate_scatter_metrics.py` - существующий скрипт валидации
- `app/data/clickhouse_loader.py:590-623` - функция load_master_metrics()
```

## 🤖 Доступные субагенты

### @code-search
**Назначение**: Поиск информации в кодовой базе БЕЗ написания кода

**Когда использовать**:
- Найти все использования функции/класса
- Определить где используется конкретная бизнес-логика
- Анализ зависимостей между модулями
- Поиск паттернов кода

**Пример задачи**:
```markdown
# Задача: Найти все файлы использующие custom_profit

## Контекст
После D014 нужно убедиться что custom_profit используется
для расчета margin_pct, а final_profit для roi_pct.

## Файлы
- `app/data/clickhouse_loader.py`
- `app/components/*.py`
- `scripts/validate_*.py`
```

### @python-refactor
**Назначение**: Рефакторинг и улучшение Python кода

**Когда использовать**:
- Упрощение сложной логики
- Удаление дублирования кода
- Улучшение читаемости
- Применение паттернов проектирования

**Пример задачи**:
```markdown
# Задача: Вынести повторяющиеся SQL фильтры в helper функцию

## Контекст
6 функций в clickhouse_loader.py дублируют одинаковые WHERE условия.
Централизовать в _build_base_filters().

## Критичные детали
- **Ограничения**: НЕ менять логику фильтрации, только вынести в функцию

## Файлы
- `app/data/clickhouse_loader.py`
```

### @code-reviewer
**Назначение**: Code review Python кода

**Когда использовать**:
- Проверка соблюдения PEP8
- Поиск потенциальных багов
- Оценка качества кода
- Проверка типизации

**Пример задачи**:
```markdown
# Задача: Code review нового модуля profit_elasticity_scatter.py

## Контекст
Модуль реализует scatter plot с LinearRegression.
Проверить корректность использования scikit-learn и обработку edge cases.

## Файлы
- `app/components/profit_elasticity_scatter.py`
```

### @qa-engineer
**Назначение**: Тестирование и валидация

**Когда использовать**:
- Написание unit/integration тестов
- Проверка корректности расчетов
- Валидация бизнес-логики
- Тестирование edge cases

**Пример задачи**:
```markdown
# Задача: Создать unit тесты для calculate_margin()

## Контекст
Функция calculate_margin() критична для корректности всех метрик.
Нужны тесты на edge cases (нули, отрицательные значения, деление на ноль).

## Критичные детали
- **Формула**: margin_pct = (custom_profit / revenue) × 100%
- **Edge cases**: revenue=0, custom_profit=0, negative values

## Файлы
- `app/utils/metrics.py:calculate_margin()`
```

## 📊 Структура эпиков и документации

### Обязательные файлы эпика

Каждый эпик: `.reports/epics/epic-XX-название/`

**4 файла**:

| Файл | Размер | Назначение | Когда обновлять |
|------|--------|-----------|----------------|
| **README.md** | ~200-300 строк | Быстрый обзор: цель, scope, timeline | При изменении SCOPE |
| **decisions.md** | ~50-100 строк | Минималистичный ADR: Решение + КРИТИЧНО + Файлы | При принятии КРИТИЧНОГО решения |
| **progress.md** | ~100-200 строк | Чеклисты задач, фазы, блокеры | После каждого батча |
| **technical.md** | ~200-400 строк | API справочник, архитектура, конфигурация | При изменении API |

### Формат decisions.md (КРИТИЧНО)

**Минималистичный формат** (экономия 80% токенов):

```markdown
## DXXX: Краткое название (YYYY-MM-DD)

[1-2 предложения что сделали]

**КРИТИЧНО**: [Только если критически важно для дальнейшей разработки]
- Примеры: терминология БД, формулы расчета, изменения API, зависимости

Файлы: `path/to/file.py`, `another/file.py`
```

**❌ НЕ включать**:
- Контекст и предысторию
- Рассмотренные альтернативы
- Плюсы/минусы решения
- Длинные объяснения

**✅ Включать**:
- Только принятое решение
- КРИТИЧНО блок (только для важного контекста)
- Список затронутых файлов

**Когда создавать запись**:
- ✅ Замена компонента/модуля
- ✅ Изменение бизнес-логики или формул
- ✅ Отказ от запланированной фичи
- ✅ Критичная терминология
- ❌ Мелкие рефакторинги без изменения API

## 🔄 Синхронизация документации

### Триггеры для обновления

**НЕМЕДЛЕННО обновить ROADMAP.md при**:

1. **SCOPE CHANGE** - изменение содержания задачи:
   - Количество компонентов (6 → 5 карточек)
   - Замена подхода (Pareto Chart → Segment Dynamics)
   - Изменение критериев успеха эпика
   - Отказ от запланированной фичи

2. **Изменение бизнес-логики**:
   - Формулы расчета метрик
   - Терминология в БД/UI
   - Структура данных

3. **Завершение фазы/эпика**:
   - Обновить статус на ✅ Завершено
   - Добавить дату и ссылку на коммит

### Действия при триггерах

**При записи решения в decisions.md с блоком КРИТИЧНО:**

1. **Определить тип изменения**:
   - SCOPE CHANGE → обновить ROADMAP.md
   - Изменение паттерна кода → обновить CLAUDE.md
   - Завершение батча → обновить feature_progress.md

2. **Обновить ROADMAP.md (при SCOPE CHANGE)**:
   ```markdown
   ~~Старая задача~~ → Новая задача (см. D005 Epic 01)
   ```

3. **Обновить CLAUDE.md (при изменении паттернов)**:
   - Profit Calculation Logic - если изменились формулы
   - Data Architecture - если изменилась терминология
   - Code Patterns - если появился новый паттерн

4. **Обновить feature_progress.md (всегда)**:
   - Добавить новый батч с кратким описанием
   - Указать ключевые файлы и изменения

### Формат обновлений

**ROADMAP.md**:
```markdown
- [x] ~~6 KPI карточек~~ → 5 KPI карточек (2025-10-14, см. D010) [коммит abc123]
```

**CLAUDE.md**:
```markdown
### Profit Calculation Logic
Маржа = Revenue - Payout
Прибыль = Маржа - Cashback - Commissions
(обновлено: 2025-10-14, см. D010)
```

**feature_progress.md**:
```markdown
## Батч 4: KPI Metrics Separation (2025-10-14) ✅

Разделены карточки "Маржа" и "Прибыль" для корректного отображения.

Файлы: clickhouse_loader.py:268-298, main.py:245,259
```

### Принцип: ROADMAP.md = Single Source of Truth

- **ROADMAP.md** всегда актуален для планирования
- **decisions.md** - история решений и детальный контекст
- **При конфликте**: ROADMAP.md > decisions.md

## 📝 Rolling Window Pattern

### feature_progress.md - Правило краткости

**Цель**: Поддерживать файл компактным для быстрого чтения AI сессиями (~2-3 минуты).

**Правило**: Активный файл `.reports/notes/feature_progress.md` содержит только **последние 5 батчей**.

**Когда архивировать**:
- При добавлении 6-го батча → переместить самый старый в архив
- Сохранить хронологический порядок (новые батчи сверху)

**Структура архива**:
```
.reports/notes/archive/
└── YYYY-QX-epicNN-batches.md
```

**Пример**: `2025-Q1-epic02-batches.md` - батчи 1-8 из Epic 02

**Формат активного файла**:
```markdown
# Feature Progress

📁 **Архив**: Батчи 1-N Epic XX → [YYYY-QX-epicNN-batches.md](archive/YYYY-QX-epicNN-batches.md)

---

[Последние 5 батчей]
```

**Обязательно при архивации**:
1. Создать файл в `.reports/notes/archive/` с батчами для архива
2. Обновить `feature_progress.md` - оставить только 5 последних батчей
3. Добавить ссылку на архив в начало `feature_progress.md`

## 📚 Дополнительные ресурсы

### Минималистичная документация

**@.reports/DOCUMENTATION_PROMPT.md** - готовый промпт для других проектов с правилами ведения компактной технической документации.

**Основные принципы**:
- Формат decisions.md: Решение + КРИТИЧНО + Файлы (без контекста/альтернатив)
- Экономия токенов: ~80% сокращение размера (411 → 86 строк в Epic 02)
- Быстрый старт: новая AI сессия понимает решения за минуту

**Когда использовать**:
- Начало нового проекта
- Запрос на обновление документации
- Добавить ссылку в CLAUDE.md проекта

- [ ] Создать `.protocol.md` в корне проекта
