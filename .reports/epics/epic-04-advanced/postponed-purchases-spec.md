Статус: Approved for Implementation

## 1. Обзор

### Цель фичи
Дать пользователю инструмент для **управления списком желаемых покупок** и подбора **безопасной даты для каждой покупки** на основе кассового календаря, чтобы не опускать баланс ниже установленной подушки.

### Проблема
- Пользователь составляет списки покупок, но забывает внести их в планирование.
- Часто не знает, "когда безопасно купить", чтобы не проваливаться ниже подушки.
- Нет визуального контроля: покупка, запланированная "наугад", может сломать месячный план.

### Решение
Виджет **"Отложенные покупки"** на Dashboard + модал управления списком + режим выбора даты в календаре (overlay на `/calendar`), где пользователь видит:
- Список фокусных покупок (priority=1) на Dashboard.
- Модал с полным списком хотелок (CRUD + "Запланировать").
- Календарь с рекомендованными и нерекомендованными днями.
- Пересчёт остатков в реальном времени при наведении на день (каскадный эффект на весь месяц).
- Возможность запланировать покупку выбором дня.

## 2. Пользовательские сценарии

### Сценарий 1: Добавление покупки в список
**Актор:** Пользователь
**Предусловие:** Пользователь открыл модал "Отложенные покупки" (клик на виджет Dashboard или кнопку "Все покупки").

**Шаги:**
1. Нажимает "Добавить покупку" внутри модала.
2. Заполняет: название (обязательно), сумма (обязательно), категория (опционально), приоритет (обязательно: 1=фокус, 2=потом).
3. Сохраняет → покупка добавляется в список.

**Результат:** Покупка видна в модале. Если priority=1 — также видна в виджете Dashboard (до 5 фокусных).

---

### Сценарий 2: Запланирование покупки
**Актор:** Пользователь
**Предусловие:** В списке есть хотелка; пользователь нажимает "Запланировать" в модале.

**Шаги:**
1. Нажимает "Запланировать" на хотелке в модале.
2. Модал закрывается. Происходит переход на `/calendar?wishlist_item=ID`.
3. Календарь открывается с overlay-баннером: "Выбор даты для: [название] ([сумма] ₽)".
4. Видит календарь текущего месяца:
   - На каждом дне: прогноз текущего остатка (без учёта покупки).
   - Рекомендованные дни подсвечены (зелёный/салатный фон).
   - На нерекомендованных днях: маркеры причин (оранжевый = подушка, красный = касса < 0).
   - Легенда вверху объясняет маркеры.
5. **Hover на день:** все суммы на календаре пересчитываются как "остаток **после этой покупки**" (каскадный эффект на все дни от выбранного до конца месяца). Маркеры/подсветка остаются неизменными (статическая карта).
6. **Клик по дню:** открывается create-modal транзакции с предзаполнением:
   - Дата: выбранный день.
   - Сумма: из хотелки.
   - Описание: "Отложенная покупка: [название]".
   - Категория: из хотелки (если задана) или null.
   - Тип: EXPENSE.
   - Если день нерекомендованный: **строка предупреждения** "Риск: подушка" / "Риск: касса < 0".
7. Подтверждает → операция создаётся.
8. Хотелка переходит в статус **"planned"**, остаётся в списке (не удаляется).
9. Query param `?wishlist_item=ID` очищается, overlay убирается.

**Результат:** Операция видна в календаре и транзакциях; хотелка помечена как запланирована с датой.

---

### Сценарий 3: Просмотр и управление хотелками
**Актор:** Пользователь
**Предусловие:** Пользователь смотрит на Dashboard.

**Шаги:**
1. Видит виджет "Отложенные покупки" с фокусными (priority=1, до 5 штук):
   - Название + сумма + статус (новая / запланирована + дата).
2. Кликает на виджет или кнопку "Все покупки" → открывается **модал "Отложенные покупки"**.
3. В модале — полный список:
   - Фокусные (priority=1) сверху, отложенные (priority=2) ниже.
   - Для каждой: название, сумма, категория, статус, кнопки [Редактировать] [Удалить] [Запланировать].
   - Кнопка "Добавить покупку" в footer модала.

## 3. Сущности данных

### WishlistItem (Хотелка)
```python
{
  id: int,
  user_id: int,
  name: str (обязательно, max 100),
  amount: Numeric(10, 2) (обязательно, > 0),
  category_id: int | None (опционально, FK на categories),
  priority: int (1=фокус, 2=потом),
  status: Literal["new", "planned"] (default: "new"),
  planned_date: date | None (дата планирования, если статус "planned"),
  planned_transaction_id: int | None (FK на Transaction, если запланирована),
  created_at: datetime,
  updated_at: datetime,
}
```

### Статусы хотелки
- **new**: добавлена, но не запланирована.
- **planned**: запланирована (есть связанная транзакция и дата).

## 4. Правила безопасности (рекомендация дней)

### Определение рекомендованного дня (MVP)
День **рекомендован**, если:
1. После добавления покупки остаток **не опускается ниже порога подушки** на этот и все последующие дни до конца месяца.
   - Порог подушки: `CushionService.get_settings(user_id).threshold_amount`.
   - Проверка: `min(balance[d:end_of_month] - amount) >= threshold` для `d >= candidate_date`.
2. **И** остаток не уходит в отрицательное значение (касса < 0) на этот и все последующие дни.
   - Проверка: `min(balance[d:end_of_month] - amount) >= 0` для `d >= candidate_date`.

> **Примечание**: Проверка бюджета целей (AllocationService) отложена на B-фазу. В MVP достаточно подушки + отрицательного баланса.

### Маркеры на нерекомендованных днях
- **Оранжевый маркер**: порог подушки нарушен (баланс после покупки опускается ниже threshold на этот или последующие дни).
- **Красное число (минус)**: касса < 0 после покупки (как сейчас в календаре).
- **Оба**: оранжевый маркер + красное число.

### Примечание
- Если касса < 0, день автоматически считается нерекомендованным.
- На нерекомендованном дне клик работает, но с предупреждением в create-modal.

### 5.4 Hover: каскадный пересчёт остатков

**Техническая реализация:**
- При открытии режима выбора даты: PurchaseRecommendationService предрассчитывает балансы для **каждого дня-кандидата** как `base_balance[d] - amount` для всех `d >= candidate_date`.
- Результат (~31 x 31 = ~960 значений) сохраняется в `dcc.Store("wishlist-hover-data")`.
- Hover реализован через **clientside callback** (JS на клиенте, без серверных вызовов).

**При наведении мыши на день:**
- Все суммы на календаре пересчитываются из Store (балансы "после покупки в этот день").
- Пользователь видит каскадный эффект: не только день покупки, но и все последующие дни до конца месяца.
- Маркеры и подсветка рекомендованных дней **остаются неизменными** (статическая карта).

**При уходе мыши (blur):**
- Суммы восстанавливаются к базовым остаткам (также из Store).

**Производительность:**
- Предрассчёт при открытии: ~200ms (один запрос к CalendarService + арифметика).
- Hover переключение: < 1ms (clientside JS, данные уже в Store).

---

### 5.5 Клик: выбор даты и создание операции

**При клике на дне (любой):**
1. Overlay убирается, query param очищается.
2. Открывается глобальная create-modal (через Preselection Store Pattern) с предзаполнением:
   - Дата: выбранный день.
   - Сумма: из хотелки.
   - Описание: "Отложенная покупка: [название]".
   - Категория: из хотелки (если задана) или null.
   - Тип: EXPENSE.
   - `modal-source`: "wishlist".

3. **Если день нерекомендованный:**
   - Сверху модалки — строка **"Риск: [причина]"**:
     - "Риск: баланс опустится ниже подушки безопасности".
     - "Риск: баланс уйдёт в минус".
   - Цвет: оранжевый/красный фон. Не блокирует сохранение.

4. Пользователь подтверждает → операция создаётся.
5. Callback слушает `global-transaction-trigger` с `source="wishlist"` → обновляет статус хотелки на "planned" с `planned_date` и `planned_transaction_id`.

### WishlistService
```python
class WishlistService:
    def __init__(self, session: Session): ...

    def create_item(self, user_id: int, name: str, amount: Decimal,
                    category_id: int | None, priority: int) -> WishlistItem
    def get_all(self, user_id: int) -> list[WishlistItem]

    def get_by_id(self, item_id: int) -> WishlistItem | None
    def update_item(self, item_id: int, **updates) -> WishlistItem
    def mark_as_planned(self, item_id: int, planned_date: date,
                        transaction_id: int) -> WishlistItem
    def reset_planned(self, item_id: int) -> WishlistItem
    def delete_item(self, item_id: int) -> bool
```

### PurchaseRecommendationService
```python
class PurchaseRecommendationService:
    def __init__(self, session: Session): ...

    def get_safe_dates_map(
        self, user_id: int, amount: Decimal, year: int, month: int
    ) -> dict[date, SafeDateInfo]
    """Возвращает карту безопасности для каждого дня месяца.

    SafeDateInfo: {safe: bool, reasons: list[str]}
    reasons: "cushion" | "negative_balance"
    """

    def precalculate_hover_data(
        self, user_id: int, amount: Decimal, year: int, month: int
    ) -> dict[str, dict[str, str]]
    """Предрассчитывает балансы для hover-пересчёта.

    Возвращает: {candidate_date_iso: {day_iso: balance_str, ...}, ...}
    Хранится в dcc.Store для clientside callback.
    """
```

### Интеграция с существующими сервисами

## 7. Технические детали

### Database
Новая таблица `wishlist_items`:
```sql
CREATE TABLE wishlist_items (
  id INTEGER PRIMARY KEY,
  user_id INTEGER NOT NULL,
  name VARCHAR(100) NOT NULL,
  amount NUMERIC(10, 2) NOT NULL,
  category_id INTEGER,
  priority INTEGER NOT NULL DEFAULT 1 CHECK (priority IN (1, 2)),
  status VARCHAR(20) DEFAULT 'new' CHECK (status IN ('new', 'planned')),
  planned_date DATE,
  planned_transaction_id INTEGER,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (user_id) REFERENCES users(id),
  FOREIGN KEY (category_id) REFERENCES categories(id),
  FOREIGN KEY (planned_transaction_id) REFERENCES transactions(id) ON DELETE SET NULL
);
```

### UI Components
- **Dashboard виджет** (в `components/dashboard.py`): read-only список фокусных хотелок + кнопка "Все".
- **Wishlist модал** (в `components/wishlist.py`): полный список, CRUD, кнопки действий.
- **Calendar overlay** (в `components/calendar.py`): overlay-баннер, CSS-классы маркеров, clientside hover callback.
- **Preselection** (в `components/transaction_modals.py`): расширение для `modal-source="wishlist"`.

### Stores (dcc.Store)
- `wishlist-active-item` — ID хотелки в режиме выбора даты (или None).
- `wishlist-safe-dates` — карта безопасности дней {date_iso: {safe, reasons}}.
- `wishlist-hover-data` — предрассчитанные балансы для hover {candidate_date: {day: balance}}.
- `wishlist-base-balances` — базовые балансы для восстановления после hover.

### Callbacks
- `open_wishlist_modal()`: клик на виджет/кнопку → открыть модал.
- `crud_wishlist_item()`: создание/редактирование/удаление хотелки.
- `navigate_to_calendar_for_purchase()`: "Запланировать" → redirect на `/calendar?wishlist_item=ID`.
- `activate_purchase_mode()`: calendar callback читает query param, загружает данные, рендерит overlay.
- `clientside_hover_recalculate()`: **clientside callback** для hover-пересчёта (JS).
- `handle_purchase_day_click()`: клик по дню в режиме покупки → create-modal с preselection.
- `mark_wishlist_planned_after_create()`: слушает trigger с source="wishlist" → обновляет статус.
- `cancel_purchase_mode()`: "Отмена" → очистка query param, убрать overlay.

### Migration
- `scripts/migrate_005_wishlist.py` — idempotent скрипт (PRAGMA table_info check перед CREATE).

## 8. Acceptance Criteria

### Функциональные
- [ ] Пользователь может добавить хотелку (название, сумма, категория опционально, приоритет 1 или 2).
- [ ] Фокусные хотелки (priority=1, до 5) отображаются в виджете Dashboard.
- [ ] Модал "Отложенные покупки" показывает полный список (фокусные + отложенные).
- [ ] В модале доступны: создание, редактирование, удаление хотелки.
- [ ] При клике "Запланировать" происходит переход на `/calendar?wishlist_item=ID`.
- [ ] Календарь показывает overlay-баннер с названием и суммой хотелки.
- [ ] Рекомендованные дни визуально отличаются (подсветка).
- [ ] На нерекомендованных днях видны маркеры (оранжевый = подушка, красный = касса < 0).
- [ ] Легенда видна и объясняет маркеры.
- [ ] При hover на день: все суммы пересчитываются каскадно (от выбранного дня до конца месяца); маркеры не меняются.
- [ ] При клике на день открывается create-modal с предзаполнением (дата, сумма, описание, категория, тип=EXPENSE).
- [ ] Если день нерекомендованный: в модалке видна строка "Риск: [причина]".
- [ ] После сохранения операции хотелка переходит в статус "planned" с датой.
- [ ] Хотелка остаётся в списке (не удаляется).
- [ ] "Отмена" в overlay → возврат к обычному календарю.

### UX
- [ ] Нет скрытых состояний: маркеры и легенда всегда видны (без hover).
- [ ] Пересчёт при hover интуитивен: суммы меняются, маркеры остаются статичными.
- [ ] Предупреждение о риске не блокирует выбор дня.
- [ ] Весь путь: Dashboard виджет → модал → "Запланировать" → календарь → клик → create-modal → сохранение.

### Performance
- [ ] Предрассчёт safe dates и hover data при открытии режима < 200ms.
- [ ] Hover-пересчёт на клиенте (clientside callback) без заметной задержки (< 5ms).

### Совместимость
- [ ] Глобальные модалки, refresh trigger, preselection store работают как в существующих фичах.
- [ ] Интеграция с CalendarService, CushionService, TransactionService без конфликтов.
- [ ] Обычный режим календаря (без query param) работает без изменений.

## 9. Не-цели (Out of Scope — MVP)

- Проверка бюджета целей (AllocationService) при рекомендации дней — B-фаза.
- Тач/мобильное поведение — B-фаза.
- Планирование нескольких покупок одновременно (MVP = одна за раз).
- Автоматическая оптимизация даты (только подсветка и выбор).
- Система уведомлений при приближении запланированной даты.
- Импорт покупок из внешних источников.

| Риск | Вероятность | Воздействие | Смягчение |

## 13. Принятые решения (из обсуждения 2026-02-04)

| # | Решение | Обоснование |
|---|---------|-------------|
| D1 | **Hover: предрассчёт в Store + clientside callback** | ~960 значений (~30KB) — ничтожно. Предрассчёт ~200ms, hover < 1ms. Каскадный эффект важен для UX — показывает последствия выбора на весь месяц. |
| D2 | **MVP scope: подушка + отрицательный баланс** (без бюджета целей) | AllocationService работает на уровне месяца, не дня. Если подушка настроена разумно, она уже покрывает "запас на цели". Бюджет — B-фаза. |
| D3 | **Без отдельной страницы. Dashboard виджет + один модал** | Для 5-15 хотелок отдельная страница избыточна. Модал — все операции в одном месте. Страница — B-фаза если список вырастет. |
| D4 | **Бинарный приоритет (1=фокус, 2=потом)** | Шкала 1-5 избыточна для MVP. Два уровня покрывают реальный use case: "хочу скоро" vs "когда-нибудь". |
| D5 | **Calendar overlay через query param** `/calendar?wishlist_item=ID` | Паттерн обкатан на `?open_recon=1`. Не добавляет заметной нагрузки поверх обычного календаря. |
