# Epic-04: Решения (Decisions)

## D001: Quick-add chips — разбивка на два протокола

**Дата**: 2026-01-25
**Статус**: Утверждено

### Контекст
Quick-add chips — это комплексная фича, которую можно разбить на два этапа: чипы категорий (простые) и шаблоны операций (сложные).

### Решение
**Разделить на два протокола:**

**Протокол A: Чипы категорий** (~6-8 дней)
- Дефолтные 5 расход + 2 доход категорий
- Клик на chip → модал создания с предвыбранной категорией
- Пользователь вводит сумму и описание
- UI: плитки с иконками (крупнее чем в Батче 3.2)
- Расположение: страница Transactions, под кнопками "Экспорт" и "Добавить"

**Протокол B: Шаблоны операций** (~6-8 дней)
- Модель Template (name, category_id, amount, description)
- 1-клик создание операции (toast "Отменить" на 3 сек)
- Кастомизация: добавление/удаление/порядок/архивирование
- Управление через "⋯" меню на каждом чипе

### Обоснование
1. **Инкрементальность** — простое (категории) → сложное (шаблоны)
2. **Ранняя ценность** — Протокол A уже дает 70% пользы
3. **Риск-менеджмент** — можно остановиться после A если B окажется сложным
4. **Тестирование** — легче протестировать и исправить баги

### Дефолтные чипы MVP (Протокол A)

**Расход (5 категорий)**:
1. Продукты (icon: `bi-cart`)
2. Дом/Жильё (icon: `bi-house`)
3. Транспорт/Авто (icon: `bi-car-front`)
4. Связь/Коммуналка (icon: `bi-phone`)
5. Развлечения/Кафе (icon: `bi-cup-straw`)

**Доход (2 категории)**:
1. Зарплата (icon: `bi-wallet`)
2. Аванс/Подработка (icon: `bi-cash-coin`)

**КРИТИЧНО**:
- Дефолтные чипы hardcoded в UI для Протокола A
- Протокол B добавит PinnedCategory модель для кастомизации
- Дефолтные чипы станут начальными закрепленными категориями после перехода на PinnedCategory

## D002: Хранение данных — отдельные таблицы вместо JSON

**Дата**: 2026-01-25
**Статус**: Утверждено

### Контекст
Для кастомизации чипов (Протокол B) нужно хранить:
1. Какие категории закреплены (pinned)
2. Шаблоны операций (templates)

Варианты:
- JSON-поле в User модели
- Отдельные таблицы PinnedCategory и Template

### Решение
**Отдельные таблицы**

### Структура

**PinnedCategory** — закрепленные категории для быстрого доступа:
```python
class PinnedCategory(Base):
    id: int
    user_id: int              # FK User
    category_id: int          # FK Category
    sort_order: int           # Порядок отображения
    created_at: datetime
```

**Template** — шаблоны операций с заполненными полями:
```python
class Template(Base):
    id: int
    user_id: int              # FK User
    category_id: int          # FK Category
    amount: Decimal(10,2)     # Сумма операции (может быть None для ручного ввода)
    description: str          # Текст описания
    name: str                 # Название шаблона (например, "Обед в офисе")
    sort_order: int           # Порядок отображения
    is_archived: bool         # Soft delete
    created_at: datetime
```

### Обоснование
1. **Консистентность архитектуры** — все domain entities как таблицы (не JSON)
2. **FK constraints** — гарантия целостности данных через БД
3. **Легко расширять** — добавить поле проще чем менять JSON schema
4. **Запросы** — JOIN проще чем парсинг JSON в SQL
5. **Миграции** — Alembic работает с таблицами, не с JSON структурами

### Trade-offs
- Больше таблиц → больше сложности схемы
- JOIN операции → микро-оверхед по производительности (незначителен для MVP)

**Альтернатива (отклонена)**: JSON-поле `user.pinned_categories` и `user.templates`
- Проще для малых объемов данных
- Проблемы с referential integrity
- Сложнее поддерживать при росте фич

## D003: UX решения для Quick-add chips

**Дата**: 2026-01-25
**Статус**: Утверждено

### Решения по UX

#### 1. Группировка по типам
Чипы разделены на две секции: "Расход" и "Доход"
```
[Расход] Продукты | Дом | Транспорт | Связь | Развлечения | Ещё...
[Доход]  Зарплата | Подработка | Ещё...
```

#### 2. Шаблон 1-клик → toast "Отменить"
```
Клик на шаблон
  ↓
Операция создана мгновенно
  ↓
Toast notification (3 сек):
  "Кофе — 150₽ добавлено [Отменить]"
  ↓
Если клик "Отменить" → удалить операцию
Если timeout → операция остается
```

**КРИТИЧНО**:
- Защита от даблтапа: 0.5-1 сек дебаунс на кнопке
- Операция из шаблона всегда на "сегодня" (date = today)

#### 3. Лимит чипов на экране
- Максимум 2 ряда (7-8 чипов видимых)
- Новые чипы добавляются в начало списка
- Старые уходят в кнопку "Ещё..." (модал с полным списком)

#### 4. Управление чипом (Протокол B)

**Удаление**:
- Hover на чип → появляется крестик (×) в правом верхнем углу
- Альтернатива: "⋯" меню → "Удалить" (архивирование)

**Редактирование шаблона**:
- "⋯" меню → "Изменить" → форма редактирования
- Можно изменить: name, amount, description, category

**Архивирование vs Hard Delete**:
- Удаление шаблона = `is_archived=True` (soft delete)
- Сохраняется история для аналитики
- Можно восстановить через "Архив шаблонов"

#### 5. Изменение порядка чипов (Протокол B)

**Отложено**: Drag-and-drop (сложность высокая)

**MVP решение**:
- Кнопки ↑↓ в "⋯" меню
- Или кнопка "В начало" (sort_order = 1, остальные +1)

#### 6. Визуальное отличие от chips категоризации (Батч 3.2)

**Quick-add chips** (крупнее, плитки):
```
┌─────────────┐ ┌─────────────┐ ┌─────────────┐
│ [🛒]        │ │ [🏠]        │ │ [🚗]        │
│ Продукты    │ │ Дом         │ │ Транспорт   │
└─────────────┘ └─────────────┘ └─────────────┘
```

**Категоризация chips** (мелкие, inline):
```
[Еда] [Развлечения] [Транспорт] ...
```

**Отличия**:
- Quick-add: иконка + текст, плитка 100-120px
- Категоризация: только текст, pill-style, 60-80px

#### 7. Расположение на странице

**Страница Transactions**:
```
┌──────────────────────────────────────────────────┐
│ Операции                          [Экспорт] [Добавить] │
├──────────────────────────────────────────────────┤
│ [Расход] 🛒 Продукты | 🏠 Дом | 🚗 Транспорт ... │
│ [Доход]  💼 Зарплата | 💵 Подработка | Ещё...     │
├──────────────────────────────────────────────────┤
│ История операций                                 │
│ ┌──────────────────────────────────────────────┐ │
│ │ 25.01  Расход  -1500₽  Кофейня              │ │
│ └──────────────────────────────────────────────┘ │
```

### Обоснование
- Минимум кликов для частых операций (цель: < 5 сек на операцию)
- Toast notification — знакомый паттерн (Gmail, Slack)
- Архивирование — не теряем данные при "удалении"
- MVP порядок (кнопки ↑↓) вместо сложного drag-and-drop

## D004: Интеграция бюджета целей с календарём — два режима

**Дата**: 2026-02-01
**Статус**: Спецификация готова

### Контекст

Пользователи не понимают, как бюджет накоплений (`monthly_savings_budget`) влияет на реальный баланс в календаре. Разрыв между планированием накоплений (Goals) и кассовым планом (Calendar) создаёт путаницу.

### Решение

**Два режима резервирования бюджета накоплений:**

#### Режим 1: "Фиксированная дата"
- Пользователь выбирает день месяца (1-31) для резервирования бюджета
- В календаре на эту дату каждого месяца создаётся виртуальная recurring операция "Резерв на цели"
- Сумма операции = `monthly_savings_budget` (фиксирована, не меняется при взносах)
- При нажатии "Внести взнос":
  - Операция в календаре НЕ создаётся
  - Только учёт распределения (GoalContribution)
  - Доступный бюджет уменьшается
- Философия: "Откладываю всю сумму → потом распределяю по целям"

#### Режим 2: "Из остатка"
- Нет фиксированной даты резервирования (default)
- При нажатии "Внести взнос":
  - Создаётся операция "Взнос: {название цели}" в календаре (на сегодня)
  - Запись в GoalContribution
  - Доступный бюджет уменьшается
- Философия: "Когда есть деньги — вношу в конкретную цель"

### Обоснование

1. **Два стиля управления финансами:**
   - Режим 1 — для тех, кто планирует заранее ("я отложил 30К, теперь распределю")
   - Режим 2 — для тех, кто действует по ситуации ("появились деньги → вношу")

2. **Философия "состояния кармана":**
   - Бюджет и подушка — это НЕ расходы, а "требования к наличию средств"
   - Режим 1: "У меня есть 30К для целей (зарезервировано)"
   - Режим 2: "Я внёс 5К в цель Ремонт (фактически)"

3. **Динамический бюджет:**
   ```
   доступный_бюджет = monthly_savings_budget - сумма_взносов_в_этом_месяце
   ```
   - Уменьшается при каждом взносе
   - НЕТ жесткого лимита (можно превысить)
   - Только визуализация прогресса (не давить на пользователя)

4. **Гибкость переключения:**
   - Пользователь может переключаться между режимами
   - История взносов сохраняется
   - Календарь автоматически обновляется

### КРИТИЧНО

1. **Операция "Резерв на цели"** (режим 1):
   - Recurring операция (использовать RecurringService)
   - Read-only (нельзя редактировать/удалить вручную)
   - Anchored-алгоритм для коротких месяцев (31 → последний день)

2. **Операция "Взнос: цель"** (режим 2):
   - НЕ INCOME, НЕ EXPENSE, НЕ TRANSFER (новый тип?)
   - Можно редактировать (изменить сумму/удалить)
   - Связь с GoalContribution (при удалении операции → удалить contribution)

3. **Без категории:**
   - "Резерв на цели" и "Взнос: цель" НЕ ИМЕЮТ категории (category_id = NULL)
   - Аналогично TRANSFER и ADJUSTMENT

4. **Визуализация прогресса:**
   - Карточка бюджета на Goals: "X из Y распределено/внесено"
   - Прогресс-бар с цветами: зелёный → жёлтый → оранжевый → красный
   - НЕТ блокировки при превышении (только warning)

### Вне scope MVP

- ❌ Перенос недовнесённого бюджета на следующий месяц
- ❌ Работа с остатками при превышении нужных сумм
- ❌ Предупреждения о недостатке средств для выполнения плана
- ❌ Автораспределение остатка бюджета в конце месяца
- ❌ Интеграция с подушкой безопасности (умное распределение)

### Открытые вопросы

1. **Тип операции "Взнос: цель":**
   - Нужен ли новый TransactionType.GOAL_CONTRIBUTION?
   - Или использовать существующий TRANSFER?
   - Или добавить флаг is_goal_contribution?

2. **Что делать с существующими взносами при переключении режима:**
   - Сохранять историю? (Да)
   - Пересчитывать "X из Y"? (Да, учитывать все взносы текущего месяца)
   - Удалять операции в календаре? (Нет, history preservation)

3. **Месяцы с меньшим количеством дней:**
   - Использовать Anchored-алгоритм из RecurringService (Да)

4. **Можно ли удалять операцию "Резерв на цели":**
   - Read-only, tooltip с объяснением (Да)

### Связь с другими фичами

- **Recurring Transactions (Батч 2)** — переиспользовать RecurringService для "Резерв на цели"
- **Goals with Priorities (Батч 2)** — взносы учитываются в расчёте доступного бюджета
- **Categories (Батч 3.1)** — операции "Резерв/Взнос" без категории (аналогично TRANSFER)
- **Safety Cushion (Батч 4.2)** — интеграция в будущем (остаток бюджета → подушка)

### Спецификация

Полная спецификация: `.reports/epics/epic-04-advanced/spec-budget-calendar-integration.md`

## D005: Исправление багов режима fixed_date — переиспользование шаблонов

**Дата**: 2026-02-02
**Статус**: Утверждено и реализовано (Протокол 0018)

### Контекст

После реализации протоколов 0016-0017 выявлены критические баги в режиме `fixed_date`:
1. При переключении `fixed_date → from_balance → fixed_date` ранее внесённые суммы "забывались"
2. Exception сбрасывался при переключении режимов — досрочный взнос терялся

**Корневая причина**: `set_mode()` создавал новый шаблон при каждом переключении → exceptions становились orphan (привязаны к старому `template_id`).

### Решение

**Переиспользовать существующий шаблон при совпадении дня:**

```python
# Логика set_mode()
if mode == "fixed_date":
    existing_template = _find_any_reserve_template(user_id)  # Включая остановленный

    if existing_template and _get_template_day(existing_template) == day:
        # Тот же день → реактивируем шаблон
        existing_template.recurring_end_date = None
        # Exceptions сохраняются!
    else:
        # Другой день → stop + cleanup + create new
        if existing_template:
            _stop_reserve_template(user_id)
            _cleanup_orphan_exceptions(existing_template.id)
        template = _create_reserve_template(user_id, day)
```

**Добавить автоматический пересчёт exceptions:**

```python
def recalculate_current_month_exception(user_id, reference_date):
    """Пересчитывает exception при изменениях.

    Вызывается при:
    - Удалении взноса (GoalService.delete_contribution)
    - Изменении суммы взноса (update_contribution_transaction)
    - Изменении monthly_savings_budget (save_budget callback)

    Логика:
    - contributions_sum до reserve_date → new_reserve = budget - contributions_sum
    - contributions_sum == 0 → удалить exception
    - contributions_sum > 0 → создать/обновить exception
    """
```

### Обоснование

1. **Сохранение exceptions** — пользователь не теряет данные при переключении режимов
2. **Корректность расчётов** — exception всегда актуален при любых изменениях
3. **Минимальная сложность** — переиспользование проще чем event-driven пересчёт
4. **Lazy import pattern** — избегаем circular dependency в GoalService.delete_contribution()

### Критичные детали

- **from_balance → fixed_date**: exceptions НЕ чистятся при переключении на `from_balance` (пригодятся при возврате)
- **Изменение дня**: stop старый шаблон + cleanup orphan exceptions + create new
- **Orphan cleanup**: удаляет exceptions только для дат после `recurring_end_date`
- **Пересчёт только для будущих дат**: `reserve_date > today` (прошлые месяцы не трогаем)

### Реализация

**Протокол 0018 (10 шагов)**:
1. Helper методы (_find_any_reserve_template, _get_template_day, _get_reserve_date_for_month, _delete_exception_for_date)
2. recalculate_current_month_exception() с расширенным _get_contributions_sum_for_month
3. _cleanup_orphan_exceptions() с логированием
4. set_mode() рефакторинг для переиспользования
5. get_budget_progress() унификация (взносы для обоих режимов)
6. GoalService.delete_contribution() с lazy import
7. Callbacks интеграция (save_budget, update_contribution_transaction)
8. 13 unit тестов
9. 3 integration теста (E2E сценарии)
10. Финализация (418 тестов passed)

### Альтернативы (отвергнуты)

- **Event-driven пересчёт через signals** — overcomplicated для MVP
- **Обновление шаблона вместо Exception** — проблема с расчётом следующего месяца
- **Виртуальный расчёт при рендере** — проблемы с производительностью

### Связь с другими решениями

- D004: Интеграция бюджета с календарём (основа)
- Протокол 0017: adjust_reserve_for_contribution() (дополняется recalculate)

## D006: Редактирование и удаление взносов — Вариант A в delete_contribution

**Дата**: 2026-02-04
**Статус**: Утверждено и реализовано (Протокол 0019)

### Контекст

GoalContribution можно только создавать — нет возможности отредактировать или удалить взнос. Существующий `delete_contribution()` содержит баг: не откатывает статус COMPLETED для `fixed_date` режима. SAVINGS_CONTRIBUTION кликабелен в calendar tooltip, что приводит к рассинхронизации данных.

### Решение

**Расширить GoalService полноценным CRUD для взносов:**

1. **update_contribution()** — обновление суммы/даты/описания с каскадной синхронизацией:
   - Contribution → Transaction (amount, date, description)
   - Goal.current_amount пересчитывается (delta = new - old)
   - Exception пересчитывается для `fixed_date` режима

2. **Переписать delete_contribution()** — исправление бага и упрощение логики:
   - Вариант A: прямое удаление без вызова `delete_contribution_transaction()`
   - Откат статуса COMPLETED → ACTIVE
   - Удаление Exception для `fixed_date` режима

3. **Calendar Guard #6** — блокировка SAVINGS_CONTRIBUTION в tooltip (аналогично SAVINGS_RESERVE)

### Обоснование

1. **Вариант A vs B** в `delete_contribution()`:
   - **Вариант A** (выбран): прямое удаление → проще, избегает дублирования логики `current_amount`
   - **Вариант B** (отклонён): делегировать в `BudgetReservationService.delete_contribution_transaction()` → дублирование логики, circular dependency

2. **Lazy import pattern** для `_get_budget_service()`:
   - Избегает circular dependency (GoalService → BudgetReservationService → GoalService)
   - Инициализация сервиса только при вызове

3. **Guard #6 критичен**:
   - Без него пользователь может отредактировать SAVINGS_CONTRIBUTION через calendar tooltip
   - Приводит к рассинхронизации: Transaction изменён, но Goal.current_amount и Exception не обновлены

### Критичные детали

- **ContributionInfo detachment** — данные сохраняются до `flush()` для защиты от detached state
- **Guards в update_contribution()**:
  - Guard #1: contribution not found → ValueError
  - Guard #2a: goal завершена → ValueError (кроме уменьшения суммы)
  - Guard #2b: уменьшение суммы у завершённой цели → откат COMPLETED → ACTIVE
  - Guard #3: description override если не передан
- **Exception recalculation** — только для `fixed_date` режима, только если Exception существует

### Реализация

**Протокол 0019 (6 шагов)**:
1. Schema + Helpers (_get_budget_service, get_contribution_by_id)
2. Service Methods (update_contribution, delete_contribution rewrite)
3. Calendar Guard #6
4. Goals UI (таблица, модалы, callbacks)
5. 23 unit тестов
